# Phase 205 修复总结：资料库文件夹提交边界与共享写者

## 发现

Phase 204 已把笔记创建/删除的事务成败与刷新、缩略图和导航分开，但文件夹链路仍保留同类问题：

1. `FolderRepositoryImpl` 的私有写锁只约束文件夹仓储实例；`NoteRepositoryImpl` 创建、更新和删除笔记使用其他事务边界，两者仍能同时修改同一 `note_meta`/`folder` store。
2. 新建、重命名、移动、删除文件夹和移动笔记都在仓储提交后继续 `getAllFolders()`、`loadNotes()` 或刷新缩略图；后处理失败会把已经提交的操作误报为失败。
3. 文件夹移动和标题保存即使排队执行，标题保存仍会把读取时的完整旧 `NoteMeta` 写回，可能撤销刚提交的 `folderId` 或录音状态。
4. 在途文件夹读取没有 mutation generation；旧 `getAllFolders()` 可以在新提交后覆盖新文件夹树。

边修边审还发现：删除当前文件夹后若只依赖一次提交后 `loadNotes()`，读取故障会让“全部笔记”只剩旧文件夹的局部卡片。仅拆异常边界还不够，仓储必须返回足以先发布的提交快照。

## 修复

- 新增 `LibraryMetadataMutationMutex.ets`，让笔记创建、导入创建、标题更新、笔记删除，以及所有文件夹/归属 mutation 共用仓储级单写者。
- 删除笔记固定 `assetMutationMutex -> libraryMetadataMutationMutex` 锁序；元数据事务提交后释放元数据锁，资产文件清理仍在资产锁内完成。
- 移除 `FolderRepositoryImpl` 私有 `writeMutex`。
- 文件夹创建、重命名和移动在事务内返回归一化后的最终文件夹快照；删除额外返回被删文件夹 ID、迁移到顶层的笔记 ID 和完整笔记元数据快照；移动笔记返回已提交目标。
- `LibraryPage` 在提交成功后立即发布这些结果；`getAllFolders()`、`loadNotes()` 和缩略图刷新改为互不决定 mutation 成败的最佳努力任务。
- 文件夹权威读取增加 read generation、mutation generation、页面 lifecycle 和 repository identity 门禁；页面重进也会独立刷新文件夹树。
- `LibraryViewModel` 增加移动笔记与删除文件夹的提交后投影，并推进 mutation generation，阻止旧列表读取覆盖已提交归属。
- 删除当前文件夹且没有搜索词时，直接使用删除事务返回的完整笔记快照切回“全部笔记”；全文搜索中先保留已知有效结果，再由权威搜索补齐。
- `NoteRepository.updateNote()` 改为原版式标题字段补丁，不再写回旧 `folderId`、`hasRecordings`、收藏和最近打开时间。
- 更新原有文件夹移动 replay，新增共享写者/提交边界专项 replay，并为 ViewModel 增加移动、删除与在途旧读取测试。

## 未闭环

- 本阶段的共享锁不是全局 RDB 事务锁；编辑器持久化、页面仓储、资产到达和同步 inbox 等其他事务域仍需继续核对跨锁交叠。
- 搜索中删除当前文件夹时，本地快照只能保留已知匹配卡片；正文索引命中的完整“全部笔记”结果仍依赖最佳努力权威查询。
- 设备上仍需覆盖：快速连续创建/移动/删除、移动后立即改标题、删除当前父文件夹、提交后注入文件夹/笔记读取失败、页面切后台再返回，以及缩略图失败不误报 mutation。
- Goal 保持 active，继续按修复总纲边修边补审。
