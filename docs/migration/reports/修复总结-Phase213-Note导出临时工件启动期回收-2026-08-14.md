## 发现

Phase 211 的录音启动清理有意只接受两种录音文件，并明确把 `.note` 导出工件留给独立生命周期审计。继续
检查 `NoteExporter.exportToFile()` 后确认存在真实进程死亡窗口：

- 导出器把完整包写到 `context.tempDir/export_<time>.note`；
- 正常成功、取消与异常路径会在 `finally` 删除它；
- 如果进程在写完临时包后、picker 交互中或复制目标文件时被杀死，`finally` 无法执行；
- 残留没有恢复记录、后续消费者或 Backup 价值，只会占用空间并保留完整用户笔记副本。

## 原版对照

- `decompiled_1.0.3/sources/defpackage/g64.java`：原版在 `cacheDir/exports` 管理私有导出目录，以
  `.created` 时间、24 小时寿命、活动集合和 500 MiB 上限决定回收。
- `decompiled_1.0.3/sources/defpackage/f64.java`：创建随机导出目录与 `.created` 标记。
- `decompiled_1.0.3/sources/com/gingerlabs/notability/data/library/state/ExportSweepWorker.java`：后台执行导出清扫。
- `decompiled_1.0.3/sources/defpackage/gv2.java` case 2：拥有者启动时删除 cache 中的 `temp_*` 与
  `*_converted.pdf` 中断工件。

Harmony 当前临时包不是可复用分享缓存，进程死亡后也没有目标 URI 恢复协议；因此复刻的是“私有导出工件
必须由拥有者在中断后回收”的生命周期，而不是机械复制原版目录、worker 和 24 小时保留期。

## 修复

- 新增 `NoteExportTemporaryArtifactCleanup.ets`：
  - 非递归扫描 `context.tempDir` 直接子项；
  - 只接受 `export_<digits>.note`；
  - 对枚举结果重新验证直接子路径，只删除普通文件；
  - 未知 `.note`、错误名称、嵌套项、目录穿越、目录外目标和同名目录全部保留；
  - 单文件与目录失败分别计数、记录并继续，不阻断数据库启动；
  - 重复执行保持幂等。
- `DatabaseManager.openAndMigrate()` 在第一次打开 RDB 前调用导出清理。所有 UI 导出入口都必须先等待数据库
  初始化，因此当前进程不存在活动导出与启动扫描重叠。
- 保留 `NoteExporter.exportToFile()` 的正常 `finally` 删除、文件句柄关闭与 `fsync`；启动清理只兜底进程
  死亡窗口。
- 新增专项 replay，锁定原版导出清扫证据、Harmony 生产者命名、启动顺序、路径门禁、与录音清理的所有权
  分离、Backup 边界和真实桌面临时目录删除/保留/幂等模型。
- 新增 `ADR-0190-note-export-temporary-artifact-startup-cleanup.md`。
