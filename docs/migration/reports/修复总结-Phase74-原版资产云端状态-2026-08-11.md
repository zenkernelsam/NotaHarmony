# Phase 74 修复总结：原版资产云端持久化状态

日期：2026-08-11

## 问题

入站同步已经能可靠回放，但原版 payload type 2 `AssetCloudPersisted` 仍会停在 deferred head。
Harmony 现有 `note_asset.status` 同时承担本地文件、下载和上传生命周期，不能直接拿来表达原版独立的
“服务器已经持有此 hash”事实，否则会把未下载文件伪装成可用，或覆盖已有本地状态。

## 原版证据

- `ra0` 只有 required field 0：内嵌 64 字节 `ua0` AssetHash。
- `v69` 收到事件后把该笔记模型中的 `za0.availability` 单调设为 `qa0.AVAILABLE`；hash 尚不存在时也创建
  空引用状态。后续资产引用合并保留已有 availability，因此事件可以先于引用到达。
- `aa6.Z` 和 `yo7` 分别消费 AVAILABLE 与 AWAITING_UPLOAD，证明它不是“本地文件已到达”的同义词。

## 修复

- 数据库升至 v52，新增 note-scoped `original_asset_cloud_state`，以
  `(note_id, canonical asset_hash)` 为主键并随笔记级联删除。行存在即表达原版单调 true 状态。
- 新增 `OriginalAssetCloudPersistedOperationApplier`：严格读取 field 0 的 64 字节 inline struct，按原版
  最低有效字节在前的原始存储顺序生成 128 位十六进制 canonical key；缺字段、截断或未知扩展字段均在写入前 deferred。
- reducer 使用 `INSERT OR IGNORE` 吸收重复事件，并接入 `OriginalPageOperationApplier` 的 supports/apply 路由。
- 明确不创建、不更新 `note_asset`，因此事件先到、引用后到仍可保留事实，也不会篡改 PENDING/LOCAL/
  UPLOADED/DOWNLOADED/FAILED 中任何本地生命周期状态。
- 顺带修正 `DatabaseHelper.test.ets` 已落后实际 v51、仍断言 v50 的旧测试漂移。

## 尚未宣称完成

本阶段只关闭 type 2 模型回放，不猜测资产上传/下载 endpoint 或调度协议。真实资产 transport、私有认证 socket、
服务端 note/site 创建仍需可靠协议证据；其余未支持 payload 和真机验收继续后续批次。
