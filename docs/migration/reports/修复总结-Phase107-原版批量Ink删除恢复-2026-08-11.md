# Phase 107 修复总结：原版批量 Ink 删除与恢复

## 原版证据

- 原版 `s83` 的 fields 0/1 是 entityDeletes/entityUndeletes operation-identity vectors；
  `fsi.d()` 将完整 List 写成一个 DELETE_ENTITIES FlatBuffer，`u5j.k/l` 不会拆成逐实体操作。
- whole erase 的 `lg2` 把命中的实体 Set 一次转为 List，再只调用一次 `fsi.d()`；这证明多笔迹擦除
  应共享一条原版 operation，而不是循环生成多个本地删除。

## 已完成修复

- persistence 从“只允许一个目标”扩展为最多 10,000 个目标的有序子序列判定。删除或恢复后的较小
  snapshot 必须是较大 snapshot 的精确子序列；每个差异项必须是 canonical `op:*` Ink，任何 payload
  修改、重排、混合元素或异常数量都会回退到 Harmony snapshot 路径。
- 一批目标现在写入同一个 entityDeletes 或 entityUndeletes vector，共享一条
  `ORIGINAL_DELETE_ENTITIES` outbound operation。原版 reducer、archive/winner、单次 page revision、
  snapshot/search 对齐与 Harmony history companion 仍在共享 mutex 和同一 SQLite 事务中完成。
- 不再错误依赖仅本地 CREATE_INK 才有的 `originalCreate` 标记；从原版包载入或远端同步的 canonical
  Ink 也可批量 whole erase。实体是否真实存在、属于当前页且 z-order 对齐，最终仍由 reducer 在事务内裁决。
- whole eraser、纯 Ink 选区删除、单步及 coalesced Undo/Redo 现都会在成功后 rearm 下一笔 CREATE_INK。
  partial erase、存活路径修改，以及同时命中 shape/text/image/math 的混合擦除仍写入 v59 authoring guard。
- 边修边审修复零命中竞态：擦除轨迹未命中、或过期选区 ID 实际未删除任何元素时，不再调用
  `persist(false)` 错误污染内存 ineligible 集合；真正的 no-op 不改变原版 authoring 资格。
