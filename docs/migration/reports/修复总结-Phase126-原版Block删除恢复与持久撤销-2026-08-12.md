# Phase 126 修复总结：原版 Block 删除恢复与持久撤销

## 原版证据与问题

- 复核原版 `u5j.k/l -> fsi.d -> s83`：type-25 的 entity delete/undelete 是统一 identity
  向量，没有把 Ink/Shape 与 Text/Image/Math Block 分开。
- 当前 reducer 本来已能处理五类页面元素，但本地 snapshot classifier 和 UI 历史资格判断仍只允许
  Ink/Shape，因此 Block 删除、恢复和持久 Undo/Redo 会退回 Harmony 快照兼容路径。
- Phase 123 虽已设计新 Text 的 Undo/Redo 使用 type-25，实际 `ADD_ELEMENT` 未进入原版 entity
  历史分类；重启后撤销链不能维持同一 Block identity。

## 已完成修复

- `StrokePersistence` 的 visibility classifier 扩展到 Stroke/Text/Shape/Image/Math，并允许五类元素
  在同一个 type-25 vector 中批量删除或恢复。
- 每个候选必须通过严格 identity 预检：snapshot row ID、payload 内 ID 和 operation ID 一致；union
  kind 与页面 kind 一致；Ink/Shape/Block 必须存在真实 child state；Text/Image/Math 的
  `block_type` 还必须分别匹配。
- reducer 执行后不再只核对 ID 与层序，同时 byte-exact 核对所有成员 payload。损坏或陈旧的持久
  history 不能在 reducer 后经 reconcile 覆盖规范内容，任一分歧整事务回滚。
- `NoteCanvasView` 接通 Text/Image/Math 的 whole eraser、选区删除、`ERASE_ELEMENTS`、
  `DELETE_ELEMENTS` 和 Text `DELETE_ELEMENT`；新原版 Text 的 `ADD_ELEMENT` Undo/Redo 也保持
  原版资格，删除与恢复使用相同 CREATE_BLOCK identity。
- 错误诊断统一从 `local Ink visibility` 更正为 `local entity visibility`，反映真实覆盖范围。

  覆盖删除、恢复、再次删除、单 revision、upload-immediate journal、Block type/payload 预检、
  新 Text Undo/Redo 源码接线和失败回滚。专项输出为：

  排除限制。全量桌面 replay 为 `TOTAL=112 FAILED=0`。
