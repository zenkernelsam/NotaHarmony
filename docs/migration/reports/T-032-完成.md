## 3. 容器层：ZIP 结构

`.note` 是全 STORE（不压缩）的 ZIP，**所有条目都在以笔记名命名的顶层目录下**：

```
OP-AMP/                      OP-AMP/Images/
OP-AMP/Session.plist         OP-AMP/PDFs/
OP-AMP/metadata.plist        OP-AMP/Assets/
OP-AMP/thumb12x.png          OP-AMP/Recordings/
OP-AMP/HandwritingIndex/     OP-AMP/Recordings/library.plist
OP-AMP/HandwritingIndex/index.plist
```

> ⚠️ **踩坑记录**：`ZipArchive.ets` 的 `ZipReader.findEntry` 是**全名精确匹配**，而目录名随笔记名变化，无法预知。因此 NoteImporter 里新增了 `findEntryBySuffix()` 按后缀匹配。这不是 ZipReader 的 bug，但任何按固定路径找条目的写法在 Notability 上都会失效。

## 5. Session.plist 结构分析

### 5.1 顶层

| 项 | 值 | 备注 |
|----|----|------|

### 5.3 InkedSpatialHash 全部 17 个键 + 数据分布

计数基准：`numcurves(NC)=1353`、`numpoints(NP)=31242`、`numfractionalwidths(NF)=11316`。

这是 **SoA（结构数组分离）** 布局，每个 blob 都是 iOS 原始内存转储。字节数**全部精确闭合**：

| 键 | 字节数 | = n × 宽度 | 校验 | 语义 |
|----|-------:|-----------|:----:|------|
| `curvespoints` | 249936 | 31242 × 8 | ✅ | (float32 x, float32 y) 中心线点 |
| `curvesazimuthunitvector` | 90528 | 11316 × 8 | ✅ | 方位角单位向量(x,y)/锚点 |
| `curvesaltitudeangles` | 45264 | 11316 × 4 | ✅ | 笔倾角/锚点（实测恒 π/2） |
| `curvesforces` | 45264 | 11316 × 4 | ✅ | 压力/锚点（实测恒 1.0） |
| `curvesfractionalwidths` | 45264 | 11316 × 4 | ✅ | 宽度系数/锚点 |
| `curveUUIDs` | 21648 | 1353 × 16 | ✅ | 每曲线 UUID |
| `options` | 10824 | 1353 × 8 | ✅ | 每曲线选项位（未解析） |
| `curvescolors` | 5412 | 1353 × 4 | ✅ | RGBA8888 |
| `curvesnumpoints` | 5412 | 1353 × 4 | ✅ | 每曲线点数（3k+1） |
| `curveswidth` | 5412 | 1353 × 4 | ✅ | **全宽**（非半宽，见 6.2） |
| `curvesstyles` | 1353 | 1353 × 1 | ✅ | 笔型（实测恒 3） |
| `numcurves` / `numpoints` / `numfractionalwidths` | UID→int | | | 计数 |
| `shapes` | UID→data 27831 | | | **内嵌 bplist**（见第 7 节） |
| `bezierPathsDataDictionary` | UID→NSMutableDictionary | | | 空（未解析） |
| `groupsArrays` | UID→NSMutableArray | | | 空（未解析） |

> ⚠️ **字节序陷阱**：plist **容器**整数是大端（big-endian），但 blob 内的 float32/uint32 是 iOS 原始内存，**小端（little-endian）**。同一文件两种字节序。ArkTS 无 `DataView`，需手动拼字节。

### 5.4 曲线几何

`curvesnumpoints[i]` 恒满足 `3k+1`，即**三次 Bézier 链**：k 段、k+1 个锚点。全篇合计 31242 点 / 11316 锚点，1353 条曲线。逐锚点属性数组（force/altitude/fractionalWidth/azimuth）长度均为 11316，与锚点数一致——这本身也交叉印证了 `3k+1` 的解读。

### 5.5 数据分布实测

| 维度 | 实测 |
|------|------|
| 颜色 | 6 种：`ff19b092`×251, `ffcf366c`×498, `ff444fad`×218, `ff3498db`×28, `ff60ba46`×353, `ff120377`×5 |
| 线宽 | 唯一值 `0.933333` |
| 笔型 | 唯一值 `3` |
| 压力 | 恒 1.0（范围 1..1） |
| 倾角 | 恒 π/2 |

压力恒 1、倾角恒 π/2 说明**本样本用的不是压感笔**（或该 iPad 未记录压感）。因此"压力映射正确"这一项**本样本无法验证**。

## 6. 坐标系与页面尺寸（含关键证明）

### 6.1 页面尺寸

`Notability.NoteDocumentPaperLayoutModel` 给出 `pageWidthDoc = 716.7999877929688`、`pageHeightDoc = 940.7999839782715`（3 页）。三条**互相独立**的证据都指向页高 940.8：

1. 官方缩略图 `thumb12x.png` 宽高比 756/576 = 1.3125，与 940.8/716.8 一致；
2. `HandwritingIndex/index.plist` 的 `pageContentOrigin` 六值精确匹配（见 6.2）；
3. 渲染平移扫描的最佳 dy = **0**（见第 8 节）。

### 6.2 `curveswidth` 是全宽——六值精确匹配

把每页中心线的 `min(x)`、`min(y)` 与 `index.plist` 的 `pageContentOrigin` 相减，三页六个值**全部**是 `+0.4667`，恰等于 `curveswidth/2 = 0.933333/2`。

这一个匹配同时钉死了三件事：`curveswidth` 是**全宽**（index 记的是渲染后外框，`curvespoints` 是中心线）、**双轴坐标解读正确**、**页高 940.8 正确**。属于证据，不是假设。

顺带解释了另一个现象：官方缩略图相对我的渲染有 +18 文档单位的 X 偏移，但**包内 index.plist 与我的 X 到小数点后 4 位一致**——所以那 18 单位是缩略图渲染器自己的内缩边距，不是我算错。

## 7. shapes 层：差点整层丢失的内容

`InkedSpatialHash.shapes` 是 UID 指向的 27831 字节 data，magic 为 `bplist00`——**它是内嵌的另一个普通 binary plist，不是归档**。三个并列数组：

```
shapes[]   每项 { appearance{style, strokeColor{rgba:[r,g,b,a] 0~1}, strokeWidth},
                  uuid(16B), options, rect:[[x,y],[w,h]], + 按 kind 不同的几何字段 }
kinds[]    'line'×96 | 'circle'×3 | 'rectangle'×1  （共 100）
indices[]  n=100, 严格递增且唯一, 值域 0..1353
```

### 7.1 `indices` 语义：证明而非猜测

`indices` 最大值 **1353 恰等于 numcurves**。若解读为"形状本身的序号"，1353 越界；只有"**插在第 i 条曲线之前**"这一解读能让 1353 成立（= 插在末尾）。加上严格递增且唯一，插入位是唯一自洽解。据此 `toStrokeElements()` 做 z 序归并：形状与曲线按绘制顺序交错输出，而非简单地全部追加到末尾。

### 7.2 形状与曲线不相交（差点丢内容）

拿 100 个形状 bbox 与 1353 条曲线 bbox 两两求交，**0/100 命中**。说明形状是曲线之外的**独立内容**——在这张运放电路图里，它们就是全部导线、圆和框。

> 🔴 **必须记录的自我修正**：在发现 shapes 层之前，我曾评价"只画曲线的渲染与官方缩略图吻合"。那是**过于乐观的判断**——实际丢了 100 个图元。只有做了像素级差异比对才暴露出来。目视"看着像"不能作为保真度结论。

### 7.3 几何还原

| kind | 源字段 | 还原方式 |
|------|--------|---------|
| `line` | `startPt`, `endPt` | 两点直线 |
| `rectangle` | `points[]`, `isClosed` | 折线（按 isClosed 闭合） |
| `circle` | `rotatedRect.corners[4]` | 椭圆**内切于该平行四边形**：由 4 角求中心与半轴 u,v，用 4 段三次 Bézier 逼近，κ = 0.5522847498307936 |

`rect` 字段恒等于几何外框外扩半线宽——**第三次**印证了半宽语义（前两次见 6.2）。

未知 kind **不猜几何**，记 warning 后跳过（任务卡明令禁止猜测数据结构）。

## 8. 保真度实测（像素级）

对照官方 `thumb12x.png`，用颜色饱和度掩膜排除灰色横线纸背景，做平移扫描：

| 渲染内容 | 最佳偏移 | Dice | 召回 |
|---------|---------|------|------|
| 曲线 + 形状（当前实现） | dx=+15, dy=**0** | **0.8961** | **92.3%** |
| 仅曲线（发现 shapes 之前） | dx=+15, dy=0 | 0.7769 | 71.97% |

形状层带来 **+0.12 Dice / +20pp 召回**。峰值锐利到 1 像素（dx=14→0.5213，dx=15→0.8961，dx=16→0.5034），说明这不是碰巧对上的宽松匹配。`dy=0` 独立复证了页高。并排目视检查内容一致：运放三角形、导线、箭头、方框、中文批注、公式全部在位。

剩余 ~8% 差异的合理来源：缩略图抗锯齿与线宽渲染差异、我未做的笔锋渐变。**未逐项归因**。

## 10. 遗留问题与后续方向

1. **真机导入未实测**（最重要的边界）。沙箱是 Linux VM，无设备工具链。已跑通的是 `check_ets_files`（四文件全部 no diagnostics）与 `build_project`（module `note`，BUILD SUCCESSFUL in 11s，exit 0）。**真机上"选文件 → 导入 → 画布显示"这条链路我没有跑过**，请指挥官在设备上验证。

2. **多页只能纵向平铺**。`StrokePersistence.saveElements(noteId, ...)` 没有页维度，且开头会 `delete` 该 noteId 全部记录——**逐页调用会互相清空**。因此 `importNotability` 一次性写入，并用 `flattenPages()` 把第 i 页整体下移 `i × pageHeightVp`。解析器仍按页返回分组，将来存储加上页维度即可直接接上。

3. **`importOurFormat()` 存在同源既有 bug**：它是逐页调用 `saveElements` 的，按上述语义会只剩最后一页。**本次未修**（超出 T-032 范围），建议单开任务。

4. **vp 坐标空间与设备相关**。当前用 `DEFAULT_TARGET_PAGE_WIDTH_VP = 360` 归一，不同屏宽下笔迹绝对尺寸会变。等 T-034 画布缩放平移落地后应改为按实际画布宽度换算。

5. **压感与笔型无法验证**。本样本压力恒 1、笔型恒 3，需要一个用 Apple Pencil 且换过笔型的样本才能验证这两条映射。

6. **样本量 = 1**。以上全部结论的置信度上限就在这里。建议再取 2~3 个含图片/PDF/录音/富文本的样本回归。
