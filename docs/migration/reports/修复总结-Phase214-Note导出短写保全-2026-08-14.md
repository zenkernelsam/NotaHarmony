# Phase 214 修复总结：Note 导出短写保全

## 发现

Phase 213 关闭了进程死亡后导出临时包永久残留，但继续检查同一导出链时发现更直接的数据完整性缺口：

- `NoteExporter` 向私有临时包和 picker 目标各只调用一次 `fileIo.writeSync()`；
- 两次调用都忽略返回的实际字节数；
- Harmony SDK 明确返回“实际写入字节数”，短写并不等同于异常；
- 旧代码会对截断文件继续 `fsync`、关闭并返回 `true`，用户得到损坏 ZIP 却看到导出成功。

仓库内图片资产与录音资产发布已经正确循环消费 `writeSync()` 返回值，说明问题集中在 Note 导出路径，而不是
项目有意接受单次写入语义。

## 原版对照

- `decompiled_1.0.3/sources/defpackage/jv5.java`：私有文件复制使用 8192 字节缓冲输出流。
- `decompiled_1.0.3/sources/defpackage/fag.java`：`z()` 循环读取 8192 字节，并把每次实际读取长度完整交给
  `OutputStream.write(buffer, 0, length)`，直到 EOF 或预算超限。

Harmony 无需照搬 Java 流类型，但必须保留“全部请求字节写完才算成功”的语义。

## 修复

- `NoteExporter.ets`：
  - 新增 64 KiB 写入 chunk 上限；
  - 新增 `writeFileFully()`，按 `writeSync()` 实际返回值推进偏移，直到完整消费字节视图；
  - 临时 `.note` 与 picker 目标统一使用完整写入；
  - 每个 chunk 继续通过 `exactArrayBuffer()` 尊重 `byteOffset/byteLength`；
  - 返回零、负数或超过本轮 chunk 长度时立即失败，避免死循环或错误推进；
  - `fsync` 仍只在完整写入后执行，中途失败沿用现有 catch/finally 关闭句柄并删除临时文件。
- 更新精确字节视图 replay，使其锁定完整写入 helper 而不是旧的一次性调用。
- 新增短写专项 replay：
  - 锁定原版 8 KiB 循环复制证据；
  - 确认两条 Harmony 写入路径均不再直接忽略 `writeSync()`；
  - 确认循环、固定 chunk、精确 view、进度门禁与 `fsync` 顺序；
  - 运行可控短写模型，验证不截断、不重复、顺序一致以及零进度失败。
- 新增 `ADR-0191-note-export-complete-file-write.md`。
