# Phase 295 修复总结：剪贴板图片可用性门禁

## 缺陷

Phase 291 后，长按菜单只要编辑器就绪且没有内部元素剪贴板就显示图片 Paste。系统剪贴板没有 PixelMap时，
用户点击后必然走权限请求或数据读取失败路径，再收到“无法添加图片”；这与原版先检查
`ClipDescription.hasMimeType("image/*")` 再分流 `ClipboardImage` 的行为不一致。

## 决策与实现

新增 `OriginalClipboardImageIngress.isOriginalClipboardImageAvailable()` 和测试注入边界。生产实现调用SDK
API 14 的 `SystemPasteboard.getMimeTypes()`，只认 `MIMETYPE_PIXELMAP`；异常一律返回 false。该探测不读取
PasteData、不解码 PixelMap，也不代替点击后的 READ_PASTEBOARD 授权。

`NoteCanvasView` 新增 `systemClipboardImageAvailable` 状态：初始和页面切换为 false；页面加载完成后异步刷新，
并继续用编辑器就绪条件 guard 异步回写。`canUseOriginalClipboardImage()` 现在必须同时满足就绪、无忙碌和探测
可用。实际 Paste 链路不变：仍先权限网关，再读取和规范化 PixelMap。

## 验证

- ArkTS fixture 覆盖可用 PixelMap、非图像、探测异常和 production probe 复位；
- 剪贴板专项 Replay 从 16/16 扩展至 20/20，覆盖 MIME exact match、fail closed、状态门禁和页面生命周期；
- 双 HAP 与全量 Replay 结果见总进展补录；
- 未启动模拟器、虚拟机、真机或 Hypium。

## 开放项

真实系统剪贴板来源矩阵、跨应用 MIME 差异、权限弹窗时机、探测时序和大图粘贴体验仍需设备验收；`T-042`
继续严格留到 Goal 最后一项。
