# Phase 286 修复总结：原版图片翻转与方向组合顺序

日期：2026-08-23（Asia/Shanghai）
状态：已完成静态顺序修复与验证；真实设备样本矩阵仍开放。

## 目标

Phase 284 后，带 EXIF 方向的图片在 renderer 中先旋转再裁剪，但 `cropRect` 仍保存 encoded bitmap 坐标。
这会让裁剪区域落到错误像素；用户 H/V flip 的作用层也不明确。本阶段补审原版共享解码证据后统一顺序。

## 原版证据

- `g3.java` case 6 先对 orientation 2/4/5/7 执行水平镜像，再执行 `w34.l()` rotation，最后绘制 oriented
  Bitmap；
- `nx0.java` 复用 `g3` 共享解码回调；
- `hp5.java` 显示 IMAGE block 独立保留 cropRect 与 horizontal/vertical flip registers。
完整记录见 ADR-0264 与 evidence 文件。

## Harmony 实现

渲染顺序固定为：

```text
block transform → scale → encoded crop clip → baked EXIF rotation/mirror → user flip → drawBitmap
```

不修改 cropRect、intrinsic dimensions、flip flags、AssetHash、CREATE_BLOCK 或资产文件。编辑画布与库页缩略图
继续共享同一 `ImageCanvasRenderer`。

## 验证

- 扩展 `ImageBlockRendering.test.ets` 覆盖用户 H/V flip 在 encoded bitmap 坐标中的 translate/scale 元数据；
- 新增专项 Replay：`d02-original-image-flip-orientation-order.mjs`；
- 专项结果：`D02_ORIGINAL_IMAGE_FLIP_ORIENTATION_ORDER_OK TOTAL=5 FAILED=0`；
- 全量 Replay、clean 双 HAP 与静态检查见总进展补录；未启动模拟器、虚拟机、真机或 Hypium。

## 明确未闭环

- Undo 后重绘、大图内存性能与端到端体验；
- `T-042` 继续严格保留为整个 Goal 最后一项。

## Phase 529 坐标契约后续

后续复核确认原版 `g3` 返回 oriented bitmap，`b40` 以 oriented `dp5.size` 解释 cropRect；因此 Phase 529
将持久化 intrinsic/crop 统一为 oriented 域，并在 raw bitmap renderer 中增加 encoded→oriented 仿射桥接。
本报告中的 encoded-crop 流程是 Phase 286 历史实现快照，当前契约以 ADR-0262/0264 的 Phase 529 澄清为准。
