# Phase 254 修复总结：原版文件夹索引拖拽与启动完整性修复

## 目标

继续收敛 M2-U-05：补齐原版 `parentId + childIndex` 拖拽排序，并把 Phase 253 只能显示的损坏 folder tree 提升为
数据库启动期确定性修复。严格保留设备验收门，不把静态实现写成完整交互完成。

## 原版复核与新发现

- `cm3/id7/sad/xdb` 证明拖拽结果包含 folderId、parentId、childIndex；`xdb` 以首项前、末项后、相邻平均值产生
  position，而不是每次追加。
- `gsi` 明确向 `im3` 传入 48dp 行高与 24dp 层级步进。进一步查看 APK `classes2.dex` 的 raw `dm3.invoke()`，确认
  横坐标按 24dp 选择 depth，纵向用 25%/75% 区间区分 before/inside/after。
- 提交前进一步复核 OpenHarmony 6.0 Release ArkUI 引擎：`ListPattern::GetItemIndexByPosition()` 从 source 尚在的
  `itemPosition_` 直接生成 `insertIndex`，经 `DragDropManager` 原样传给 drop callback。由此确认向下拖动必须先扣除
  落点前 source 可见子树，当前实现不会产生偏一位。
- 当前草稿虽已有 ArkUI drag callback，但只按相邻行 parent 推导，且 UI 缩进为 12vp；没有横向意图也可能意外嵌套。
  本阶段在写 Report 前继续修正为原版 24dp 横向深度语义。
- Phase 253 只隔离 cycle 的误删与 UI 不可达；数据库版本不变的旧用户仍不会得到 orphan/cycle/超深层级修复。

## 代码修复

- 新增 `FolderHierarchyRepair.ets`：保留全部 folder/ID/名称，确定性修复 missing parent、self-parent、cycle、超过
  六层和 sibling order 异常。
- `DatabaseManager` 在每次启动的统一 repair transaction 内、外键检查前执行 folder hierarchy repair；异常整体
  rollback，错误文案扩展为通用 startup repair failure。
- `FolderRepositoryImpl` 新增 `FolderMovePlan`、`FolderDropIntent`、`planFolderMove()` 与 `resolveFolderDrop()`；
  `moveFolder` 支持 insertIndex，并在同一事务写回旧/新父级完整兄弟序列。
- 原版 fractional position 适配为连续 child index。可见顺序和 childIndex 契约一致，同时避免重复平均值的精度风险。
- `LibraryPage` 的 regular/compact tree 统一为共享 `List`，接入长按拖拽；拖拽快照固定可见 ID/depth/source/x anchor，
  以 24vp 横向步进计算目标 depth，整棵子树作为一个移动单位。
- 提交前源码审阅发现 `onItemDragStart` 若返回 `void`，ArkUI 引擎会得到空自定义节点并终止起拖；现补
  `FolderDragPreview` builder 并从回调返回，修掉“静态编译成功但实际长按不起拖”的潜在运行时 bug；页面离开时
  同步清空 drag snapshot，避免迟到 drop 在已离开的资料库页面继续提交移动。
- 菜单新增“上移/下移”作为键盘、无障碍及拖拽失败后备；中英文资源齐全。
- 更新 Phase 251 的 `Scroll` 证据与 replay，使其反映当前共享 `List`，避免正确重构触发假回归；更新旧 sibling-order
  replay，使其验证计划序列写回而非已经淘汰的实现形态。
