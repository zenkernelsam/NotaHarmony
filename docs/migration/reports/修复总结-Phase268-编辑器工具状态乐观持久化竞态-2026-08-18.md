## 修复前真实缺陷

### ToolState 连续失败恢复到未确认值

旧 `updateState()` 把本次调用前的 `before` 当作回滚值：黑色→红色失败，随后红色→蓝色也失败时，第二次会恢复红色。
红色从未写入数据库，最终 UI 与 repository 不一致。

### Toolbox selection 有同类持久前缀错误

连续 Pen→Pencil、Pencil→Highlighter 的 toolbox 保存都失败时，第二次以乐观 Pencil 为 `oldActiveId` 并恢复它；
数据库仍是 Pen。旧失败还把 `selectionVersion` 恢复旧值，破坏 generation 单调性。

### Shapes preference 连续失败恢复到错误值

初值 true，连续请求 false、true 且两次均失败时，第二次会恢复第一次的 optimistic false；Preferences 仍是 true。

### Eraser await 的迟到成功和失败都会覆盖后续选择

Partial/Whole Eraser 先等待 `setEraserIsPartial()`：

- 保存失败时旧代码无条件恢复旧 active/previous，覆盖等待期间的新选择；
- 保存成功时旧代码继续 `applyActiveState()` 和保存旧 toolbox，也会把新选择重新切回 Eraser。

### 重新初始化可能越过 pending 保存

同一个 ViewModel 若在旧 ToolState 保存尚未结束时再次 `initialize()`，旧代码会先读取 repository 的旧值并重建 UI，
旧保存随后才落盘；重入完成时 UI 已旧、数据库已新。

## 实际修改

### 三类 committed snapshot

- `committedStates`：每个 tool ID 的最后成功 ToolState；
- `committedToolbox`：最后成功的 active/previous selection；
- `committedShapeDetectionEnabled`：最后成功的 Shapes preference。

初始化从实际加载/补全结果建立 baseline；repository 为 null 的纯内存路径也同步确认当前值。

### FIFO 持久前缀与最新失败回滚

保存仍使用共享 FIFO `saveChain`。每个成功项无条件推进对应 committed snapshot，即使 UI 已有更新的 optimistic version；
失败不改 committed，只在自己的 version 仍为最新时把 UI 恢复到当前持久前缀。因此：

- A/B 都失败 → 回初值；
- A 失败、B 成功 → 保留 B；
- A 成功、B 失败 → 回 A。

### 单调 version 与 Eraser supersession gate

- ToolState 继续按 tool ID 分版本；Shapes preference 新增独立 version；selection version 只递增；
- rollback 不再恢复旧 generation；
- Eraser mode `await` 返回后再次检查 selection version。若已有新工具选择，迟到成功只保留已写成的 mode，迟到失败只
  返回失败；二者均不得 apply/persist 旧 Eraser selection。
- `initialize()` 先进入 loading 并等待已有 `saveChain`，旧 continuation 完成后才清空 baseline、替换 repository 并重读。
