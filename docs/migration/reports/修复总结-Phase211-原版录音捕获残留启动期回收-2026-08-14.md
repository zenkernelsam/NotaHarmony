本阶段开始时重新核对 Goal、提交和工作树：Phase 210 提交 `cdb9b6f` 完整存在，`main` 仍领先

## 发现

Phase 210 已处理 `assets/pending` 与 `assets/trash`，但调查原始 capture backend 后确认还存在独立的真实缺口：

- `OriginalRecordingMicrophoneBackend` 在 `context.tempDir` 创建
  `recording_<time>_<sequence>.m4a`；
- `OriginalRecordingInternalAudioBackend` 在同一目录创建
  `internal_recording_<time>_<sequence>.m4a`；
- 正常 stop 后持久化、启动/停止失败和 abort 都会删除输出，但进程在录制或交付持久化前被杀死时，进程内
  清理逻辑无法执行；
- `tempDir` 不在系统 Backup 的 `filesDir/databaseDir` 快照中，也没有下次启动消费者，因此残留会持续占用
  私有空间。

这不是系统自动临时目录语义足以替代的边界：系统可以回收 cache/temp，但没有保证在下一次应用启动前逐个
删除这些捕获文件；原版则有明确的拥有者启动清理。

## 原版对照

- `decompiled_1.0.3/sources/defpackage/gv2.java` case 13 在录音拥有者启动时清空
  `temp_recordings` 与 `AudioCaptures` 的直接子文件。
- `decompiled_1.0.3/sources/defpackage/tr8.java` 在 `filesDir/temp_recordings` 创建普通录音输出。
- 原版 `AudioCaptureService.java` 在 `filesDir/AudioCaptures` 创建捕获 PCM 输出。

Harmony 不需要复刻 Android 的目录和 PCM→AAC 实现，但必须复刻“未完成录音仅属于当前会话；拥有者下次
启动回收上次运行孤儿”的生命周期语义。

## 修复

- 新增 `OriginalRecordingCaptureArtifactCleanup.ets`：
  - 非递归扫描 `context.tempDir` 直接子项；
  - 只接受 `recording_<digits>_<digits>.m4a` 与
    `internal_recording_<digits>_<digits>.m4a`；
  - 对枚举结果重新验证直接子路径，只删除普通文件；
  - 未知文件、嵌套项、目录穿越、目录外目标和名称伪装目录全部 fail closed 保留；
  - 单文件与目录失败分别计数、记录并继续，不阻断应用数据库启动；
  - 返回 scanned/removed/skipped/failed 统计，重复执行保持幂等。
- `DatabaseManager.openAndMigrate()` 在第一次打开并发布 RDB 前执行 capture 清理。
  `NotePage` 只有等待数据库初始化并加载页面后才显示录音面板；store 发布后后续 `initialize()` 不再扫描，
  因此不会在正常运行中删除当前会话的活动捕获。
- 保留麦克风/设备内录 backend 的 stop/abort 回收和 `OriginalRecordingPersistence` 的发布后 `finally` 删除；
  启动清理只是进程死亡窗口的兜底，不改变正常录音路径。
- 新增专项 replay，锁定原版证据、Harmony 生产者命名、启动顺序、路径门禁、非递归行为、正常消费路径、
  Backup 边界和真实桌面临时目录上的删除/保留/幂等模型。
- 新增 `ADR-0188-original-recording-capture-startup-cleanup.md`。
