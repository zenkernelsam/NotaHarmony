# Phase 215 修复总结：系统 Backup 清单完整写入

## 发现

Phase 214 修复 Note 导出短写后，继续枚举仓库中忽略 `fileIo.writeSync()` 返回值的路径，确认系统 Backup
manifest 存在更严重的原子集合破坏窗口：

- `writeText()` 单次写入 `nota-backup-manifest.json`，不检查返回值；
- 写完后不 `fsync`、不校验长度；
- 正数短写不会进入异常路径，`createSnapshotLocked()` 会继续发布 staging；
- 发布流程会用该损坏集合替换上一份有效 snapshot，并在成功路径删除 previous；
- 备份状态仍可能显示完成，直到恢复时 JSON 解析失败才暴露。

因此它不是普通日志或状态文本问题，而是系统备份集合的提交标记被错误判定成功。

## 原版与现有协议对照

- `decompiled_1.0.3/sources/defpackage/fag.java`：私有文件复制按 8192 字节循环读取并完整写出每个实际读取块。
- 移植侧 `copyFileVerified()` 已对快照对象执行长度和逐字节校验；manifest 作为集合索引必须采用同等级或更强
  的发布门禁。
- 现有 staging/previous 回滚只在写入错误能够抛出时生效；旧短写被误判成功会绕过这套保护。

## 修复

- `NoteBackupAbility.writeText()`：
  - 复用 64 KiB `COPY_BUFFER_SIZE` 分块写入；
  - 按 `writeSync()` 实际返回值循环推进，直到完整消费 UTF-8 view；
  - 每个 chunk 从 `byteOffset + total` 精确切片，不写入 view 外字节；
  - 拒绝零、负数或大于请求长度的进度；
  - 完整写入后执行 `fsyncSync()`；
  - 关闭后验证普通文件身份和最终长度。
- 保持调用顺序：manifest 完整返回后才设置 `publishing` 并移动/发布目录。
- 任一失败继续进入既有外层 catch：删除 staging、标记失败并保留上一份 snapshot。
- 更新备份文本精确字节 replay。
- 新增系统 Backup manifest 完整写入 replay，锁定原版循环复制证据、短写循环、view 边界、进度门禁、
  `fsync`/长度验证、发布顺序、staging 清理以及桌面短写模型。
- 新增 `ADR-0192-system-backup-manifest-complete-write.md`。
