# Phase 204 修复总结：资料库提交刷新与缩略图生命周期

## 发现

M2-U-04 的共享 mutation chain、删除事务回滚和有限缩略图 worker 已经存在，但仍有三个会直接破坏用户体验的剩余竞态：

1. 创建或删除事务已提交后，紧随其后的 `loadNotes()` 失败仍被提示为写失败；重试创建会产生重复空笔记，删除成功后则可能保留旧卡片。
2. 页面离开会立即异步释放旧 `ThumbnailRenderer`，而已有 worker 可能仍在使用它；worker 又动态读取 `this.thumbRenderer`，还可能错误调用刚换入、未初始化的新 renderer。
3. `aboutToDisappear()` 取消资产可用性订阅，但 `onPageShow()` 没有恢复；同时旧初始化和旧缩略图任务缺少完整页面生命周期身份，可能在重进后发布过期状态。

边修边审还发现：只用读取 generation 不足以阻止“先开始读取、期间提交写操作、最后旧读取覆盖新快照”。

## 修复

- `LibraryViewModel` 增加 mutation generation；读取期间发生提交时，旧结果被丢弃并自动重复当前查询。
- 创建提交后，在点击时的视图仍有效且新笔记匹配当前查询时直接发布仓储返回的 `NoteMeta`；删除提交后直接移除卡片。写结果不再等待权威列表读取。
- 页面在删除后独立执行缩略图刷新和权威 reload；这些后处理失败只写日志，不再显示“删除失败”。
- 创建与导航拆成两个错误边界：创建失败使用 `create_note_failed`，创建成功但打开失败使用新增的 `created_note_open_failed`，明确告知笔记已经创建。
- 创建提交后也启动独立权威 reload；若搜索命中规则或索引状态与本地标题投影不同，列表会在不影响导航和提交结果的前提下校正。
- 每次缩略图刷新固定捕获 renderer 与 lifecycle generation；所有 worker 检查同一身份，禁止跨生命周期发布。
- 页面离开先失活并推进 lifecycle/thumbnail generation，再换出 renderer；旧 renderer 通过 `thumbnailRefreshMutex` 等待所有在途 worker 完成后释放。
- 页面激活抽为幂等 `activatePage()`，`aboutToAppear()` 与 `onPageShow()` 都恢复资产订阅。
- 初始化、返回资料库加载、搜索索引回填和缩略图发布均增加页面 active、lifecycle generation、ViewModel/renderer identity 门禁。
- Hypium 增加“创建提交后读取失败”“删除提交后读取失败”“在途旧读取被创建提交失效”的测试。
- 更新原有 mutation/图片缩略图 replay，并新增生命周期专项 replay。

## 原版对照

原版 `decompiled_1.0.3/sources/defpackage/veb.java` 观察 `ClientNoteUpdate`、`SyncedNoteMetadata`、`PermanentlyDeletedNote`；`x17.java` 将它们合并为资料库查询。该结构证明原版的 mutation 与资料库观察流分离，不能用一次手工 reload 的成功与否定义写事务结果。

Harmony 没有照搬原版 Room/Flow，而是用本地确定性快照、mutation generation 和最佳努力权威 reload 保持接近原版的用户语义。缩略图 renderer 的互斥退役则是 Harmony PixelMap/native 资源所有权所需的平台修复。
