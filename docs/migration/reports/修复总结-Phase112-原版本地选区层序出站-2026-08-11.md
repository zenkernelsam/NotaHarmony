# Phase 112 修复总结：原版本地选区层序出站

## 原版证据

- 原版 `dhb` 的四个层序入口并非同一命令：case 6/7 经 `py(..., 26)` 做逐层移动，case 8/9 经
  `cfc(9/8)` 做置前/置后。Harmony 当前菜单文字和 `movePageElementRefs` 行为属于后者。
- `zh9.p` 以 unsigned uint64 zIndex 排序页面 unit，构造 `ZIndexData` 后调用 `cfc`；结果经
  `x0j.a(list, true)` 生成 type 24，并由 `xsc.i` durable 提交。
- `cfc case 9` 保持选区内部顺序，从当前最大 zIndex 后依次加一；case 8 从当前最小值开始排列选区，
  只压移会与新低位区间冲突的未选 unit。原版 Group 是一个层序 unit，不能把成员叶子当成独立对象重排。

## 已完成修复

- `StrokePersistence` 新增严格 pure-reorder classifier：原版页面 identity、当前层序快照必须对齐，前后成员
  完全相同，所有元素 payload 逐字节不变，最终排序必须精确等于 Harmony 目标；任何混合内容、额外字段变化、
  重复/缺失选择、全页选择或状态冲突继续走既有保守 fallback。
- 使用十进制字符串实现原版 uint64 分配并检查最大值。置前从最大值后递增；置后只改选区及确实冲突的低位
  未选元素，不把稀疏页面无谓全量重编号，也不经不安全 JS number 转换。
- 页面存在与当前元素相交的 active 原版 Group 时拒绝出站。此处刻意等待 Group identity/writer 完成，不用
  叶子数组顺序冒充原版 Group-unit 行为。
- 数据库升级至 v60，新增 `original_local_z_order_history`，按 `(note_id, action_id)` 保存本次变化目标的精确
  before/after uint64 映射，并按笔记保留最近 512 条。映射在 reducer 成功后与 type-24 journal、snapshot、
  history companion 位于同一事务，失败会整体回滚。
- PUSH 要求当前 original zIndex 等于 before 并生成/保存映射；UNDO 要求当前等于 after 后恢复 before；REDO
  要求当前等于 before 后恢复 after。重启后从 durable history actionId 读取同一映射，不用数组下标猜测逆操作。
- `NoteCanvasView` 在置前/置后 PUSH 时传递复制后的命令和完整选择 ID；Undo/Redo 不依赖临时 hint。全 canonical
  原版重排继续保持下一笔 CREATE_INK authoring eligible。
