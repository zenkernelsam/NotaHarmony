# Phase 73 修复总结：原版入站同步回放与 ACK 边界

日期：2026-08-11

## 问题

Harmony 已分别具备上传协调器、持久 `synced_operation_inbox`、原版 operation reducer，以及可保存
`NOTE_BUNDLE / OPS_BUNDLE / RECEIVE_OPS_EVENT` 的 deferred 表，但这些组件互不接线。尤其是入站
socket 事件没有原版 FlatBuffer 解包入口，现有 reducer 在生产路径上收不到远端 operation；若 adapter
自行在解析后立即 ACK，还会在数据库失败时永久丢失服务端重送机会。

## 原版证据

- `vt9` 是 `OpsBundle(ops, schemaVersion)`；`zgb` 是
  `ReceiveOpsEvent(ops, expectedAckReply, schemaVersion)`，两者的 ops 均为原版 `uq9`。
- `kx` 收到 `receive-ops` 后解析 `zgb`：空批可立即 ACK，非空批先送入有背压的 channel。
- `kb9` 先等待 `jh2.invoke(list)` 完成整批模型处理，再遍历各 `zgb` 发出其
  `expectedAckReply`。因此“二进制解析成功”不是可靠 ACK 点。

## 修复

- 新增 `IncomingOperationSyncCoordinator`，严格按原版字段号解码 `vt9/zgb`，无损读取 uint16 schema、
  required ACK reply 和 operation vector；没有猜测 endpoint、认证或额外 wire 字段。
- 为 FlatBuffer reader 新增嵌套 table 重定根：复制整个 bundle，只改前四字节 root offset 指向原 `uq9`。
  operation 的 ID、client/server time、payload union 及所有引用字节均不重编码，继续交给既有严格 validator；
  复制前按现有 128 MiB 入站批预算检查总分配量，拒绝“大包 × 多 op”内存放大。
- 入站次序固定为：完整预检 → `receiveBatch()` 原子入箱 → `processHead()` 顺序 drain → ACK。
  EMPTY 与持久 DEFERRED 均是可 ACK 边界；解析、入箱、reducer 或 ACK 调用失败均不伪造成功。服务端精确重试
  由 inbox 的 identity + metadata + bytes 幂等核对吸收，冲突重试仍拒绝。
- 原版空 receive event 在 required ACK reply 校验后立即 ACK，不会错误地 drain 或被本地旧 deferred head 阻塞。
- `OPS_BUNDLE` 和 deferred `RECEIVE_OPS_EVENT` 进入同一路径；重放前重新检查长度、CRC32、原版三值 type、
  FlatBuffer root 及 row/payload schema 一致性。`NOTE_BUNDLE` 继续走页面身份与内容同事务，禁止错误旁路。
- 提供 production factory，将协调器明确绑定现有 `SyncedOperationInboxStore` 与
  `OriginalPageOperationApplier`；真实私有 socket adapter 仍留待取得可验证协议后实现。

## 验证

- 新增 `d02-incoming-operation-sync.mjs`：真实布局构造 `zgb/vt9`，验证两次 `uq9` 重定根、字段无损、
  apply 后 ACK、精确重试、deferred 后 ACK、故障不 ACK，以及 OPS bundle 不产生 socket ACK。
- 新增并注册 `IncomingOperationSyncCoordinator.test.ets`，覆盖解码、durable receive/reducer drain/ACK
  调用顺序与异常抑制；`note@ohosTest` ArkTS 编译和打包通过。
- 全量桌面 replay：`TOTAL=60 FAILED=0`。
- clean 后 `note@ohosTest`、`note@default` 双 HAP 均 `BUILD SUCCESSFUL`。
- 按约束未启动模拟器/真机，未执行设备 Hypium。

## 尚未宣称完成

本阶段完成的是可注入、可静态证明的入站处理链，不代表真实云服务已连通。私有认证 socket adapter、服务端
note/site 创建、断线重连和真实 ACK 发射仍需可靠凭据与协议证据。真机还需覆盖接收中断线、杀进程后恢复、
重复投递、未知 payload durable deferred，以及 ACK 严格晚于恢复应用。
