# Phase 210 修复总结：资产临时工件启动期回收

## 发现

重启后先核对了 Goal、工作树和最近提交：Phase 208/209 均完整存在，分支只保留三个明确不得暂存的
`.codex-tmp-*` 目录，没有丢失代码。

随后复核 `OriginalPencilWidthGeometry.ets` 的 `unsupported original Pencil width rebuild`。该异常只拒绝
非 Pencil、非法宽度、空路径或无法按原版中心路径重算的损坏快照；正常本地宽度修改以及入站原版
`MODIFY_INK` 已分别重建 splat 和 bounds。直接删除门禁会把坏数据静默写回，因此没有把它误判为缺失
实现。

继续检查 Phase 207 的未闭环项后确认了真实缺口：

- `assets/pending` 的图片/录音临时文件在写入或发布中途杀进程后会残留；
- `assets/trash` 的隔离文件在 detach 后、unlink 前杀进程后会残留；
- 系统 Backup 会排除二者，但此前没有任何启动期消费者，残留只会永久占用空间。

## 原版对照

- 原版 `decompiled_1.0.3/sources/defpackage/gv2.java` case 13 在管理器启动时清空
  `temp_recordings`、`AudioCaptures`。
- 同文件 case 2 在启动时清理 `temp_*` 与 `*_converted.pdf`。
- `p29.java`/`zq6.java` 证明资产管理器与已发布 `assets/final` 的所有权边界。

因此本阶段复刻的是“拥有者启动时回收上次运行的私有临时工件”，同时保留 Harmony 原子发布与规范
hash 文件的现有适配方式。

## 修复

- 新增 `AssetTemporaryArtifactCleanup.ets`：
  - 非递归扫描 `assets/pending`、`assets/trash`；
  - 只接受 `pending_asset_*`、`pending_recording_*`、`deleted_asset_*` 的精确数字命名；
  - 只删除普通直接子文件，未知文件、嵌套路径、伪装目录和目录外路径全部保留；
  - 单文件/单目录失败独立记录，不因一个垃圾文件阻断应用数据库启动；
  - 返回 scanned/removed/skipped/failed 统计，清理可重复执行。
- `DatabaseManager.openAndMigrate()` 在首次打开 RDB 前执行清理。由于 `RdbStore` 尚未发布，当前进程内
  依赖数据库的资产写者不可能已经运行；后续 `initialize()` 直接复用已打开 store，不会在正常运行中
  重复扫描。
- 新增 `d02-asset-temporary-artifact-startup-cleanup.mjs`，锁定原版证据、三类生产者命名、启动顺序、
  非递归与路径门禁，并在真实桌面临时目录重放删除、保留和幂等行为。
- 新增 `ADR-0187-asset-temporary-artifact-startup-cleanup.md`；ADR-0184 的规范路径 detach 协议保持不变。
