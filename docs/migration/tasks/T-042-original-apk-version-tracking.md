## 目的

当原版 Notability Android APK 发布新版本时，以可复现、抗混淆的方式比较旧版与新版，快速识别新增功能、
行为变化、数据格式/operation/schema 变化、资源变化和已修 bug，并将差异映射为 NotaHarmony 的新增、完善、
优化或回归任务，提高后续移植效率、完整性和准确性。

当前已知本地基线包括 `1.0.1` 与 `1.0.3`；正式执行时必须重新核验版本名、versionCode、APK/XAPK 组成、
SHA-256 与反编译工具链，不得直接把历史对话中的版本信息当权威证据。

## 最终交付物

1. 建立 `docs/migration/version-tracking/`，至少包含：
   - 原版 APK 版本基线总表；
   - 统一的版本接收、哈希、反编译和复核流程；
   - 每一组相邻版本的差异报告模板与实际报告；
   - 原版语义符号映射表，以及差异到 NotaHarmony 文件/任务/replay 的影响矩阵。
2. 记录每个版本的：
   - `versionName`、`versionCode`、package、split/ABI/resource 组成；
   - APK/XAPK SHA-256、文件大小、来源与接收时间；
   - JADX/JDK/命令行参数和任何 show-bad-code、反混淆或手工恢复步骤；
   - Manifest、Room DDL、FlatBuffers/operation、资源、native library 与关键行为证据。
3. 比较时不得只按 `defpackage` 文件名或混淆类名做结论。应结合稳定字符串、字段形状、调用关系、实现接口、
   payload/schema、资源引用和行为 fixture 建立跨版本语义映射；若升级了 JADX，旧版本也必须用相同工具参数
   重新生成后再比较，避免把反编译器变化误报为 App 变化。
4. 对每项差异标记：新增、修改、删除、仅重排/混淆变化、证据不足；再标记 NotaHarmony 状态：不适用、已对齐、
   部分对齐、待实现、需设备验证。所有待实现项必须落到任务卡和专项 replay/fixture。
5. 本任务完成时必须新增独立 Phase 修复总结 Report，写明：
   - 建立了哪些追踪文档与工具；
   - 覆盖了哪些原版版本和证据；
   - 发现并派生了哪些迁移任务；
   - 哪些差异仍因混淆、设备或样本不足无法闭环；
   - 如何复现下一次版本接入流程。
6. 在最终 Wiki、技术文档与新手入门中归纳集成：明确版本追踪文档的功能、入口、适用场景、阅读顺序，说明
   “新增原版版本后从哪里登记、如何生成差异、如何把差异转成修复任务”，不得让它成为只有原作者知道用途的
   孤立文档。

## 验收标准

- 至少完成 `1.0.1 → 1.0.3` 的基线重放，并能用同一流程接入一个未来版本。
- 每个被引用的 APK、反编译文件和手工恢复文件都有版本号与 SHA-256；报告中不再出现无版本限定的
  `defpackage/xxx.java` 权威引用。
- 原始文件清单差异与语义差异分层展示；混淆名改变不会自动被判断为功能新增/删除。
- 每个确认的行为变化都能追溯到原版证据，并明确其 NotaHarmony 影响、任务状态和验证入口。
- 独立 Phase Report、Wiki/技术文档入口和新手入门说明均已落盘并互相链接。

## 当前不做

- 不在核心修复尚有大量高优先级任务时执行全量版本重反编译或语义 diff。
- 不把 APK/XAPK 大文件提交进 NotaHarmony Git 仓库；仓库只记录可验证的哈希、元数据、证据路径与报告。
- 不因原版新版本改变而无审查地覆盖已证明正确的 `1.0.3` 语义；任何升级都必须明确兼容策略与目标版本。
