### A-01 【P1】段间连续性修正投影了错误的向量（p3-p0 而非 p1-p0）

- 移植侧：`note/src/main/ets/core/algorithm/CubicFitter.ets:209-234`（`applyContinuity`）
- 基准证据：`reference/defpackage/sqh.java:310-329`

```java

gp2 gp2Var2 = (gp2) arrayList3.get(i5);
a81 a81Var3 = gp2Var.b;   // p1
a81 a81Var4 = gp2Var.a;   // p0
double d2 = a81Var3.a - a81Var4.a;   // p1.x - p0.x
double d3 = a81Var3.b - a81Var4.b;   // p1.y - p0.y
...
double d8 = (d3 * d7) + (d2 * d6);   // dot(p1-p0, unit(prevTangent))
a81Var2.a = d6 * d8;
a81Var2.b = d7 * d8;
gp2Var2.b = a81Var2.d(a81Var4);      // p1 = proj + p0
```

`gp2` 字段序在 `reference/defpackage/gp2.java:8-22` 与 `toString()`（第 452 行 `"CubicCurve(p0=" + this.a + ", p1=" + this.b + ", p2=" + this.c + ", p3=" + this.d`）双重确认：a=p0, b=p1, c=p2, d=p3。✅

- 差异：移植侧 `CubicFitter.ets:224-225` 写的是
  `const dx = cur.p3.x - cur.p0.x; const dy = cur.p3.y - cur.p0.y;`
  即把**段端点弦向量**投影到前段切向，而原版投影的是**本段控制向量 p1-p0**。
  由于原版是就地覆写 p1（`gp2Var2.b = ...`），投影的正是 p1 自身的手柄向量；用弦向量替代会让手柄长度变成弦长而非拟合出的手柄长，几乎每条多段笔画的形状都会偏离（手柄普遍被拉长，曲线更"鼓"）。
- 修复指令：把 `dx/dy` 改为 `cur.p1.x - cur.p0.x` / `cur.p1.y - cur.p0.y`；`len === 0`（前段切向退化）分支同样改用 `p1-p0` 作为偏移（原版 `dSqrt == 0` 时 `a81Var2 = (d2, d3)`，即原样保留 p1-p0）。
- 验收标准（静态）：`applyContinuity` 内不出现 `cur.p3`；两处偏移源均为 `cur.p1.* - cur.p0.*`。单测：构造两段，前段 `p2=p3`（切向为 0），断言修正后 `cur.p1` 与修正前完全相等。

### A-09 【P1】时间加权 lerp 完全缺失，`smoothingWindow` 被当作"预留参数"从未参与计算

- 移植侧：`note/src/main/ets/core/algorithm/ForceSmoother.ets:7`（注释「默认 8（dr4 参数，**窗口预留**）」）、`:44-53`（smooth 主体）
- 基准证据 ✅：`1.0.1 defpackage/yc4.java:115-133`

```java
if (dr4Var.a) {                                  // enabled
    double dE = jp3.e(dr4Var.b);                 // smoothingWindow（毫秒）
    double d3 = ((dr4) d30Var.J).c;              // maxForceChangePerPoint
    Double d4 = (Double) d30Var.K;               // 上一次平滑后的 force
    Long   l  = (Long)   d30Var.L;               // 上一个点的时间戳
    if (d4 != null && l != null) {
        long jLongValue = jA - l.longValue();    // dt = 本点时间 - 上点时间
        if (jLongValue < 0) jLongValue = 0;
        double dT = me8.t(jLongValue / dE, 0.0d, 1.0d);   // t = clamp(dt / window, 0, 1)
        dC = me8.t(((d4.doubleValue() * (1.0d - dT)) + (dC * dT)) - d4.doubleValue(),
                   -d3, d3) + d4.doubleValue();
    }
    d30Var.K = Double.valueOf(dC);
    d30Var.L = Long.valueOf(jA);
}
```

化简后原版是**两步**：

```
t       = clamp(dt / smoothingWindow, 0, 1)
blended = last * (1 - t) + raw * t            ← 第一步：按时间间隔做线性插值
force   = clamp(blended - last, -max, +max) + last   ← 第二步：增量钳制
```

- 差异描述：移植侧 `ForceSmoother.ets:44-53` **只实现了第二步**，且插值那一步的输入直接用了 `raw`：

```ts
let force: number = p.pressure;                    // 相当于强制 t = 1
if (this.lastForce >= 0) {
  const delta: number = p.pressure - this.lastForce;
  if (delta > max) force = this.lastForce + max;
  else if (delta < -max) force = this.lastForce - max;
}
```

  即移植侧等价于**恒定 `t = 1`**。`p.elapsedTimeMillis` 字段在整个 `smooth()` 中从未被读取，`smoothingWindowMs` 也从未参与运算——注释里的"窗口预留"四个字就是这个缺陷的自白。
- 后果推演：`t` 只有在 `dt >= window` 时才等于 1。默认 window = 8ms，于是：
  - 120Hz 采样（dt ≈ 8.3ms）→ t ≈ 1，移植与原版**几乎一致**，所以在普通设备上测不出来；
  - 240Hz 手写笔（dt ≈ 4.2ms）→ t ≈ 0.52，原版会把新压力值与上一值各取一半再钳制，移植侧不做插值 → **压力曲线明显更抖**，落笔与收笔处的粗细跳变更硬；
  - 事件合并/批量上报导致 dt 很小时（dt → 0）→ t → 0，原版几乎完全保持上一压力值（强平滑），移植侧仍按 raw 走满 ±0.15 的钳制额度 → 单帧内多点时压力剧烈摆动。
  这正是 MatePad + M-Pencil 这类高采样率设备上"笔迹粗细发抖"的直接来源。
- 修复指令：`smooth()` 内维护 `lastTimeMs: number = -1`；对每个点：

```ts
const dt: number = this.lastTimeMs < 0 ? 0 : Math.max(0, p.elapsedTimeMillis - this.lastTimeMs);
const t: number = Math.min(1, Math.max(0, dt / this.config.smoothingWindowMs));
let force: number = p.pressure;
if (this.lastForce >= 0) {
  const blended: number = this.lastForce * (1 - t) + p.pressure * t;
  const d: number = Math.min(this.config.maxForceChange,
                    Math.max(-this.config.maxForceChange, blended - this.lastForce));
  force = this.lastForce + d;
}
this.lastForce = force;
this.lastTimeMs = p.elapsedTimeMillis;
```

  `reset()` 同步把 `lastTimeMs` 置回 -1。注意原版对 `dt < 0` 是**钳到 0**（不是丢弃该点），必须照做。
- 验收标准（静态）：`ForceSmoother.ets` 中 `smoothingWindowMs` 出现在除构造/接口定义之外的运算表达式里；`smooth()` 读取了 `p.elapsedTimeMillis`；存在 `lastTimeMs` 字段且在 `reset()` 中被重置；`:7` 的「窗口预留」注释被删除。
- 证据等级：✅（原版算法逐行可证）

### A-22 【P1】起点/终点半圆帽的角度整体偏了 90°，轮廓在两端不闭合

- 移植侧：`WidthOutlineBuilder.ets:100-114`（`buildRoundCap`）、`:32-35`（调用）、`:38-50`（组装）
- 差异描述：这是**移植侧自身逻辑的确定性错误**，无需基准即可判定。推演如下。

  设某端点处切向单位向量的方位角为 `θ_t`。由 `:80` 法向量定义 `normal = (-ty, tx)`，即法向是切向逆时针旋转 90°，故 `baseAngle = atan2(normal) = θ_t + π/2`。

  轮廓组装顺序是（`:38-50`）：`startCap → upper 正序 → endCap → lower 逆序 → 闭合`。要构成一条不自交的封闭多边形，两个帽必须满足：
  - **起点帽**：从 `lower[0]`（= 中心 − normal·hw，方位角 `baseAngle + π`）出发，经过**后方** `−tangent`（方位角 `θ_t + π = baseAngle + π/2`），到达 `upper[0]`（方位角 `baseAngle`）。即起始角 `baseAngle + π`，扫 −π。
  - **终点帽**：从 `upper[n−1]`（方位角 `baseAngle`）出发，经过**前方** `+tangent`（方位角 `θ_t = baseAngle − π/2`），到达 `lower[n−1]`（方位角 `baseAngle + π`，等价 `baseAngle − π`）。即起始角 `baseAngle`，扫 −π。

  而代码实际是（`:104-107`）：

```ts
const startAngle = isEnd ? baseAngle + Math.PI / 2 : baseAngle - Math.PI / 2;
const sign      = isEnd ? -1 : 1;
const a         = startAngle + sign * (Math.PI * i) / segments;
```

  - 起点帽（isEnd=false）：从 `baseAngle − π/2` 扫到 `baseAngle + π/2`。端点方位角是 `θ_t`（**正前方**）与 `θ_t + π`（正后方），经过 `+normal`。
  - 终点帽（isEnd=true）：从 `baseAngle + π/2` 扫到 `baseAngle − π/2`，端点是正后方与正前方，经过 `+normal`。

  两个帽都**旋转了 90°**：画出的是"法向侧的半圆"，而不是"端部的半圆"。后果是多边形在四处出现跳变——`startCap` 末点（中心 − tangent·hw）与 `upper[0]`（中心 + normal·hw）不重合，`upper` 末点与 `endCap` 首点不重合，`endCap` 末点与 `lower[n−1]` 不重合。
- 用户可见现象：笔画两端出现凸起的"耳朵"或缺角；粗笔尤其明显；封闭路径填充时端部形状不对称（起点与终点的畸变方向相反）。
- 修复指令：`buildRoundCap` 改为

```ts
const startAngle: number = isEnd ? baseAngle : baseAngle + Math.PI;
const sign: number = -1;   // 两个帽都是 −π 扫描
```

  并补一条断言/单测：`buildRoundCap` 返回的首点应等于 `center + normal*hw*(isEnd ? +1 : -1)`，末点应等于 `center + normal*hw*(isEnd ? -1 : +1)`。
- 验收标准（静态）：单测断言起点帽首点与 `lower[0]` 的距离 < 1e-9、末点与 `upper[0]` 的距离 < 1e-9；终点帽首点与 `upper[n-1]`、末点与 `lower[n-1]` 同理。
- 证据等级：✅（纯几何推演，确定性）

## 6. ShapeDetector.ets（基准 `decompiled_1.0.3/resources` 字符串 + `com/myscript/iink`）

### A-30 【P1】触发时机错误：原版是「画完后继续按住」才识别，移植侧是「笔画完成即识别」

- 移植侧：`ShapeDetector.ets:1` 文件头注释「§24：直线/椭圆/多边形，**笔画完成时触发**，失败保留手画」；调用侧 `NoteCanvasView.ets:438` 在抬笔路径上直接 push `REPLACE_ELEMENT`
- 基准证据 ✅：`decompiled_1.0.3/resources/res/values/strings.xml`

```xml
<string name="feature_settings__use_the_pen_pencil_or_highlighter_to_draw_a_shape_then_continue_to_hold_down_to_automatically_detect_it">
  Use the pen, pencil, or highlighter to draw a shape, then continue to hold down to automatically detect it.
</string>
```

  这是原版设置页里对该功能的官方说明：**画出形状后「继续按住不抬笔」才会自动识别**（hold-to-detect）。
- 差异描述：两者的交互语义完全不同。原版是用户**主动表达意图**（按住不放）才替换成规整图形，不想要就正常抬笔；移植侧是**每一笔抬笔后都尝试识别并替换**。后果：
  - 用户随手画的短横、勾、圈会被意外"拉直"成直线或正圆，手写笔迹被破坏；
  - 由于 `confidenceThreshold` 只有 0.5（`:30`），误触发率会相当高；
  - 域4 的 R-28 已指出替换判定用"点数不同"当作识别成功，进一步放大误替换。
- 修复指令：改为按住触发——抬笔前若指针在末点附近**静止超过阈值时长**（原版具体时长未定位，需另出定位卡；可先取 500ms 作为移植方假设并标注），才触发识别与替换；抬笔即结束则保留手画笔迹。识别成功时应有视觉/触觉反馈（原版 `HapticPreferencesInitializer.java` 的存在提示可能有振动反馈，🟡）。
- 验收标准（静态）：识别调用不在抬笔（touchUp）路径上，而在按住计时器的回调中；`NoteCanvasView` 中存在该计时器的建立与在移动超阈值时的取消。
- 证据等级：✅（原版字符串直述行为）

### A-31 【P1】缺少「形状识别」开关，原版是可关闭的设置项

- 移植侧：`ui/settings/` 下无对应开关（域5 审计的 27 条中亦无此项）
- 基准证据 ✅：`resources/res/values/strings.xml` 存在 `<string name="feature_settings__shapes_detection">Shapes detection</string>`，命名前缀 `feature_settings__` 表明它是设置页的一个条目。
- 差异描述：原版允许用户关闭形状识别。移植侧无法关闭，叠加 A-30 的误触发问题后，用户没有任何逃生出口。
- 修复指令：在设置中增加「形状识别」开关，默认值需确认（原版默认值未定位，🟡）；关闭时 `ShapeDetector` 整条路径短路。
- 验收标准（静态）：设置页存在该开关且其值被识别调用点读取。

### A-32 【P2 ❓】全部判据常量为移植方自拟，原版识别引擎是 MyScript iink

- 移植侧：`ShapeDetector.ets:26-30`（`lineThreshold 0.6` / `lineMinLength 60` / `ellipseMaxGap 120` / `refitThreshold 5.0` / `confidenceThreshold 0.5`）及内联常量 `:113` 的 `0.5`/`60`、`:166` 的 `0.8`、`:190` 的 `0.55`/`0.05`
- 基准证据 🟡：反编译源含 `com/myscript/iink/` 共 92 个类（`Engine`、`Editor`、`ContentPart`、`HandwritingResult`、`GestureAction` 等），配套有 `HandwritingPackDownloadWorker.java`、`LanguagePackUnavailableException.java`、`MathRecognitionUnsupportedException.java`。原版的识别能力建立在**第三方 SDK（MyScript iink）**之上，而非手写的几何判据。
- 差异描述：移植侧用一套自拟的几何启发式（直线拟合度、椭圆归一化误差、多边形简化点数）替代了 iink。这是**合理的工程折衷**（iink 是商业 SDK，无法移植），但必须明确：
  - 上述 9 个常量**没有任何原版依据**，不能声称"与原版一致"；
  - 识别质量与原版不可比，调参只能靠移植方自己的主观测试；
  - `isAvailable()` 恒返回 `true`（`:52-54`），而原版在语言包/手写包未下载时是**不可用**状态（`LanguagePackUnavailableException`）——移植侧没有对应的降级路径，但因为不依赖外部包，这一点可以接受。
- 修复指令：不改数值。在文件头补一段声明：「本实现为移植方自研几何启发式，**原版使用 MyScript iink SDK**，两者识别行为不可比；以下常量均为移植方经验值，无原版依据」。防止后续工人误以为这些数字来自逆向。
- 验收标准（静态）：文件头含该声明；各常量处标注"移植方经验值"。
- 证据等级：❓（原版无同类实现可比对）
