## 二、结论先行

当前版本离“完美移植和可放心使用”仍有明显距离。最危险的不是按钮文案或小样式，而是以下六条端到端链路尚未闭环：

| 优先级 | 链路 | 当前后果 | 主批次 |
|---|---|---|---|
| P0 | 页面保存与快速切页并发 | 旧快照可能覆盖新快照；迟到的旧页加载结果可能显示在新页 | M2-DATA |
| P0 | 元素持久化主键 | `client_op.op_id` 全局主键，导入副本或跨笔记复用元素 ID 会冲突 | M2-DATA |
| P0 | WebDAV 备份集合一致性 | 部分上传也写“上次备份成功”；恢复只取目录中最新单个文件 | M2-BACKUP |
| P1 | 原始输入样本链 | 历史点、抬笔终点、真实时间、倾角/方位角/工具类型仍丢失 | M2-INPUT |

| P1 | 解析器资源预算 | ZIP、binary plist、keyed archive 对敌意长度/对象数/压缩比没有总预算 | M2-FORMAT |

这六条没有闭环前，不应把项目描述为“功能完成，只剩打磨”。

## 四、批次 M2-DATA：数据身份、顺序和并发

### M2-D-01 P0：`client_op` 使用全局 `op_id` 主键

**现场**：`DatabaseHelper.ets` 仍为 `op_id TEXT PRIMARY KEY`；`StrokePersistence` 又让 stroke 和 text 共用这一命名空间。自有格式导入副本会保留元素 ID，第二份笔记可能与第一份发生主键冲突。

**原版**：`e47.java:336` 是 `(noteId, opId)` 复合主键。

**修复指令**：

- 新数据库至少改为 `PRIMARY KEY(note_id, op_id)`。如果本批同步引入统一元素表，推荐明确到 `(note_id, page_id, element_id, kind)`。
- 数据库版本递增，写真实迁移：建新表、复制、校验行数、替换旧表、重建索引；不得只改 `CREATE TABLE IF NOT EXISTS`。
- 定义 stroke/text 同 ID 的策略。若仍分 kind，唯一键必须包含 kind；若统一为 NoteElement，ID 必须在一篇笔记内唯一。
- 导入副本回归必须覆盖“两个包保留相同 note/element ID”的场景。

**验收**：两个副本均导入成功，两个 noteId 均可独立加载、修改、导出；旧 v3 数据无丢行；迁移中途失败会回滚。

### M2-D-02 P0：加页的 `MAX(page_index)+1` 存在竞争

**现场**：`PageRepositoryImpl.addPage()` 先 SELECT MAX 再 INSERT，没有事务；`page_info(note_id,page_index)` 也没有唯一约束。`PageManagerBar` 和 `NotePage` 没有 busy 门禁，连续点击可并发加页/删页。

**2026-08-16 重放进展**：当前 `addPage()` 已进入共享 editor persistence mutex 与 SQLite transaction，UI
已有页操作 busy 门禁，原版 identity 对齐笔记由生产 CREATE_PAGE reducer 分配真实页面身份并返回数据库物化页。
Phase 244 又修正普通新页为 page-background-null、从 note `SET_METADATA` winner 继承。并发 20 次的集成测试与
设备交互仍应按本节验收执行；本段只撤销上述已过时现场，不把整个 M2-D-02 标为设备验收完成。

**修复指令**：

- 加 `(note_id, page_index)` 唯一索引并提供迁移前去重/重排策略。
- `addPage()` 的读最大值和插入放进同一事务；冲突需有限次重试或串行化。
- `NotePage` 增加页操作 busy 状态；加、删、设置、前后翻页在写操作完成前禁用。
- 仓储返回数据库实际分配的 `pageIndex`，UI 不得用 `pages.length` 自行假设。

**验收**：并发触发 20 次加页后 index 必须是连续且唯一的 `0..N-1`；失败不出现 UI 幽灵页。

### M2-D-03 P0：`persist()` 无序 fire-and-forget

**现场**：`NoteCanvasView.persist()` 直接调用异步 `saveElements(...).catch(...)`。连续落笔、擦除、文本提交时多个“删后全量重写”事务的完成顺序不受控，旧快照可最后提交覆盖新快照；传入数组也没有在入队时做不可变快照。

**修复指令**：

- 以 `(noteId,pageId)` 为键建立单写者保存队列；每次入队复制 stroke/text 快照并分配单调 revision。
- 合并尚未开始的旧保存，只保留最新 revision；已开始的保存串行完成。
- 页面切换、离页和返回库页必须 `await flush(pageId)`，不能只触发保存。
- 保存失败保留 dirty 状态并提示重试，不能只打印日志。

**验收**：注入延迟，让 revision 1 比 revision 2 晚返回，最终数据库必须是 revision 2；离页前 flush 失败时不得假装保存成功。

### M2-D-04 P0：快速翻页的异步结果可串页

**现场**：`switchPageData()` 在 `await loadElements()` 后再次读取动态 `currentPage.pageId`，也没有 generation/request token。A→B→C 快速切换时，B 的迟到结果可能覆盖 C。

**修复指令**：

- 进入函数时捕获 `fromPageId`、`targetPageId` 和 request generation。
- 保存旧页使用捕获的旧页快照；加载目标页使用捕获的 target ID。
- 只有 generation 仍最新且父组件当前页仍等于 target 时才发布到 UI。
- 页面写操作 busy 与加载 busy 分开；失败时恢复到明确页面并显示错误。

**验收**：人为设置 B 加载 300ms、C 加载 10ms，最终可见页和 `loadedPageId` 必须都是 C，B 数据不得写到 C。

### M2-D-05 P1：快照表仍被命名为 op-log

**现场**：`StrokePersistence` 每次删除单页全部记录并重写，`OpStore` 仍零实现，`op_type` 恒为 INSERT，`client_time` 只是排序序号。这不是原版 append-only op 语义，也不能支撑跨会话 Undo 或增量同步。

**修复决策**：不得继续把快照伪装成 op-log。二选一并写 ADR：

- 短期方案：正式命名为 page element snapshot，去掉虚假的 op 类型语义，使用明确 revision/element order；Undo 仍是会话级。
- 保真方案：实现真正 op store、op 组合、回放、压缩和持久化 Undo。此方案工作量大，必须单独设计迁移。

**验收**：接口、表名/字段和行为描述一致；不得出现“叫 op 但每次全删”的半模型。

### M2-D-06 P1：适配模型缺关系约束

**现场**：`page_info.note_id`、`client_op.note_id/page_id`、`note_meta.folder_id` 没有外键；page index 只有普通索引。

**修复指令**：围绕 Harmony 自己的适配模型补外键和复合唯一约束，启用外键检查；迁移前扫描孤儿页、孤儿元素、孤儿 folder 引用并形成可恢复修复策略。不要宣称这些列逐列来自原版 Room。

**验收**：删除 note/page 的级联或显式事务行为唯一且有测试；数据库拒绝插入孤儿元素和重复页序。

### M2-D-07 P1：原版工具状态模型没有接到主程序

**现场**：全仓除定义文件外没有 `ToolRepositoryImpl` 调用；`EditorViewModel` 只有一份共享 `brushColor/brushWidth/brushStyle`。Pen、Pencil、Highlighter 会相互覆盖状态，重启也不能恢复。

**原版**：`e47.java:376-382` 为每种工具持久化 color、width、style、选中色/宽井、自由选区和局部擦。

**修复指令**：定义编辑器工具状态单一真相源；按 tool type 保存独立状态；启动加载、切工具、改颜色/宽度/样式、擦除/选区模式都通过 repository；处理加载期间 UI 和失败回滚。

**验收**：三种书写工具分别设置不同颜色/宽度，来回切换和重启后均保持；自由选区与像素擦状态也保持。

**2026-08-18 Phase 268 现场更正**：上述主接线已完成，但“写失败只回滚最新变更”的旧实现仍把调用前的
optimistic 值当成确认值。连续 A/B 均失败时，B 会恢复到同样失败的 A；Toolbox selection 与 Shapes preference

## 五、批次 M2-INPUT：输入、拟合和铅笔保真

### M2-A-01 P1：没有历史/合并采样点

**修复指令**：查明当前 API 21 ArkUI/PenKit 可获得的 historical/coalesced 数据接口，按事件时间排序送入 `InputBatchKind.HISTORICAL` 和 REAL；同一 pointer 去重。若 ArkUI 不暴露此能力，完成报告必须给 SDK 证据并评估 PenKit/XComponent 输入通道，不能静默认定“不需要”。

### M2-A-02 P1：抬笔最终点未采样

**验收**：Down(0,0)→Up(10,0) 的最终笔画包含终点；Cancel 不产生完成笔画。

### M2-A-03 P1：时间、压力 sentinel 和工具类型不符合契约

**现场**：`toRawPointerEvent()` 使用 `Date.now()`、`toolType: 0`；无 pressure 时写 0，而 `InputPoint` 契约明确要求 -1。0 表示真实零压力，与“不支持”不同。

## 八、批次 M2-FORMAT：解析完整性和资源预算

### M2-F-01 P1：BinaryPlistParser 仍会把局部错误包装成成功

**现场**：

- 不支持高位 `0x7` UTF-8 string。
- 对象 offset 只检查 `< offsetTableOffset`，没有要求 `>= 8`，可指向 `bplist00` header。
- array/dict 子对象失败时塞 null，之后根仍可返回；`parse()` 在设置 `out.value` 前没有检查 `ctx.error`。
- date 接受整个 0x3 系列，没有限定标准 marker `0x33`。
- 没有对象数、字符串/data 长度、总分配量预算。

**修复指令**：按规范补 marker；将“允许的循环引用占位 warning”和“结构损坏 error”分离；任一非容错子对象错误使根失败；所有乘加先做溢出/预算检查。

**验收**：每个 marker、offset 指向 header、坏子引用、伪 date、超大 length、深层容器都有恶意样本测试；不得 OOM 或长时间卡死。

**2026-08-17 Phase 267 现场更正**：上述“允许的循环引用占位 warning”已经被 Phase 163 的 hard failure
淘汰，不能再作为验收口径。现场重放又发现 offset table/trailer 未要求精确闭合、ref/offset 宽度未验证承载
能力、fill 被当 null、`0xB` ordered-set 被降级为 ARRAY，以及重复 dict key 在 Apple last-wins 与 Harmony
first-wins 间分叉。现按 `CFBinaryPList.c:788-822,1072-1097,1299-1437,1573-1579` 全部 fail closed；三份
tracked OP-AMP plist 保持合法。详见 ADR-0245、Apple evidence 与 Phase 267 replay。

### M2-F-02 P1：NSKeyedArchiverDecoder 缺归档身份与 UTF-8 校验

**现场**：不校验 `$version`；`$archiver` 无 allowlist；UID 越界静默 null；手写 UTF-8 不校验 continuation、overlong、surrogate 和码点上限。

**修复指令**：允许 `NSKeyedArchiver` 和有证据的 `GLKeyedArchiver`，未知归档器拒绝或显式 UNSUPPORTED；限定版本；UID 越界结构化报错；改用严格 TextDecoder 或实现完整验证。

**验收**：越界 UID、overlong NUL、孤立 continuation、UTF-16 surrogate、>U+10FFFF 全部拒绝或替换并上报，不能静默生成错误标题。

**2026-08-17 Phase 267 补充**：archive 完整值图现在独立拒绝重复 plist 字典键，即使值不是由
BinaryPlist parser 构造，也不能绕过该门禁。选择整体失败而非 first/last-wins，避免归档身份、对象表或业务字段
被重复键遮蔽。

### M2-F-03 P1：Session/metadata 的“部分成功”判定仍会漏报内容丢失

**现场**：

- 没有 Handwriting Overlay/SpatialHash 时提前 `ok=true`，typed/media 内容尚未盘点。
- 页数推导只看 curves，不看 shapes；`pageCountHint` 小于内容推导页数时仍绝对采用，内容被钳到末页。
- `decoded.warnings` 和 metadata parser warning 没有全链传播；metadata 关键字段全空仍可能成功。
- 未知 shape、曲线 mismatch 和 style 退化会丢保真度，但 PARTIAL 判定并非按“已知内容总量与落地量”计算。

**修复指令**：建立内容 inventory：handwriting、shape、text、image/PDF、audio、metadata；先盘点再决定 SUCCESS/PARTIAL/CORRUPTED；pageCount 取不丢内容的上界并对冲突告警；所有 parser warning 合并去重。

**验收**：纯键入、纯媒体、纯形状、hint 偏小、metadata 空、未知 shape 各有样本，报告精确列出恢复和丢失数量。

### M2-F-04 P1：ZIP 缺安全预算和头部一致性校验

**现场**：无条目数、单条/总解压大小、压缩比预算；不拒绝重复文件名；不检查分卷字段；Local/Central 的 name、flags、method、CRC、size 没有逐项一致性校验；Zip64 仍不支持。

**修复顺序**：先做预算、重复名、分卷拒绝和双头一致性，再单独做 F-08 Zip64。Zip64 不能成为推迟安全限制的理由。

**验收**：zip bomb、10 万空条目、重复 manifest、local/central 名称不一致、伪 size、分卷、合法 Zip64 均有测试和明确结果。

### M2-F-05 P2：压力、变宽和 style 仍被压成普通定宽笔

**现场**：现有样本 pressure/style 证据不足，当前选择告警后退化。这比瞎猜安全，但离保真导入仍远。

**任务**：收集带 Apple Pencil 压感、荧光笔、铅笔、虚线/点线的原版 `.note` 样本；做字段相关性分析并建立可复现映射。没有样本前只保留告警，不得伪造映射。

## 九、批次 M2-BACKUP：WebDAV 和系统备份

### M2-B-01 P0：远端目录、错误和 XML 语义混在一起

**现场**：`remoteNotePath('')` 产生 `<backupPath>/.note`，恢复却用它做目录 PROPFIND；`listDir()` 把 HTTP/网络失败吞成 `[]`，UI 将“服务器失败”显示为“没有备份”；XML 仍用正则且不检查每个 `propstat/status`。

**修复指令**：拆分 `backupDirectoryUrl()` 与 `noteObjectUrl(id)`；list 返回结构化 success/error；使用可用 XML parser，按 DAV namespace、response、propstat、status 解析，只接受成功 propstat 的字段，并过滤目录自身响应。

**验收**：207 中混合 200/404 propstat、默认 namespace、任意前缀、相对/绝对 href、401/500/超时都有测试；失败不得显示为空目录。

### M2-B-02 P0：备份不是一个可恢复的原子集合

**现场**：每篇 note 单独 PUT，部分甚至全部失败后仍写 `lastBackup`；恢复按 mtime 只下载整个目录最新的一个 `.note`，无法恢复“某一次的全部笔记”。导出期间各篇笔记也可能来自不同时间快照。

**修复指令**：

- 每次备份生成 batchId、临时目录/前缀和 manifest，manifest 记录 noteId、文件名、size、hash、updatedAt、schema/version。
- 所有 note 上传并校验成功后，最后原子发布 manifest/完成标记；失败批次不可见为成功。
- 恢复先列完整批次，让用户选批次或默认最新完成批次，再逐项校验 hash；允许部分恢复但必须报告。
- `lastBackup` 只在完成标记成功后更新，并使用同一个时间值。
- 备份开始时获取一致性快照或逐篇记录 revision，检测导出中途变化。

**验收**：第 2/3 个上传失败时无成功时间、无可恢复完成批次；完整批次能恢复所有笔记；篡改一个对象只使该项 PARTIAL。

### M2-B-03 P1：配置保存可能撕裂，密码故障被当成空密码

**现场**：先写 AssetStore 密码，再 flush 普通配置；后一步失败会留下新密码配旧 URL。`loadPassword()` 把 AssetStore 故障降级为空密码，和“用户未配置密码”不可区分。

**修复指令**：使用 versioned config 和两阶段提交/补偿；密码记录绑定 config generation；加载返回 found/not-found/error 三态；保存失败恢复旧完整配置；清密码时不能吞非“not found”错误。

**验收**：对 AssetStore add/remove/query 和 preferences.flush 的每个失败点做 fault injection，重启后只能得到旧完整配置或新完整配置。

### M2-B-04 P1：系统 Backup Ability 仍是空壳，设置返回不刷新

**现场**：`NoteBackupAbility.onBackup/onRestore` 只写日志；BackupPage 从设置页返回后没有可靠 onPageShow reload。

**修复指令**：若产品声明支持 Harmony 系统备份，则按 CoreFileKit 契约真正注册数据库/资产并处理版本恢复；否则移除 extension 和用户暗示。BackupPage 每次显示时重新加载配置并区分 loading/error/ready。

## 十、批次 M2-UI：可达性、工具状态和产品完整性

### M2-U-01 P1：工具能力仍不可达或互相覆盖

**现场**：brushStyle 没有 UI 入口，TAPER/DASH/DOTS 在活跃编辑器不可达；selectionIsFreehand 没入口；三种书写工具共用单一颜色/宽度/style；shape detection 只有内存开关，没有持久设置。

```text
M2-00 现场重放/冻结批次边界
  |
  +--> M2-DATA 身份、迁移、单写者、切页 generation
  |       |
  |       +--> M2-EDITOR 统一元素、Undo、剪贴板、形状
  |
  +--> M2-INPUT 原始样本与算法
  |       |
  |       +--> M2-RENDER 最终落笔、缓存与截图差分
  |
  +--> M2-FORMAT 解析安全与内容盘点
  |       |
  |       +--> M2-BACKUP 批次 manifest 和完整恢复
  |
  +--> M2-UI 可达性、主题、产品入口
          |
          +--> M2-RELEASE 全量回归、模拟器、真机
```

建议派工粒度：每次 2-4 个高度相关文件，边审边写完成报告。不要把 `NoteCanvasView`、全部解析器和全部 UI 同时交给一个长任务；前轮已经证明长任务在断线时会丢失全部调研。

冲突热点：

| 文件 | 允许的主批次 | 纪律 |
|---|---|---|
| `NoteCanvasView.ets` | INPUT → DATA → EDITOR → RENDER 顺序进入 | 同一时间只允许一个写者 |
| `StrokeTypes.ets` / `ElementTypes.ets` | INPUT、EDITOR | 契约方案先审后改 |
| `DatabaseHelper.ets` / `DatabaseManager.ets` | DATA | 所有 schema 改动合并成连续迁移 |
| `NoteImporter.ets` | FORMAT、DATA、BACKUP | 先完成格式报告模型，再接备份恢复 |
| `Canvas2DStrokeRenderer.ets` / `StrokeLayerManager.ets` | RENDER | renderer 行为和缓存架构分两个 commit/报告 |

## 十二、测试与验收总表

当前真正有业务断言的测试主要是 `ZipArchive.test.ets` 和 `EraserEngine.test.ets`，其余多为模板；而且修复进展只证明测试源码能编译，没有证明测试已经被 runner 执行。必须补以下套件：

| 套件 | 必测内容 | 层级 |
|---|---|---|
| InputPipeline | historical/current/up/cancel、时间、pressure=-1、tool/tilt/orientation | 纯单测 + 设备事件 |
| PersistRace | 无序保存、离页 flush、A→B→C 迟到加载、失败重试 | 仓储集成测试 |
| DatabaseMigration | v1/v2/v3→新版本、复合主键、唯一页序、FK、并发加页 | 临时数据库 |
| ImportDuplicate | 同 ID 包导入两次、stroke/text 同 ID、回滚清理 | 导入集成测试 |
| UndoMatrix | 所有操作 undo/redo、跨页、施加失败回滚、淘汰策略 | 纯单测 + UI |
| ParserHostile | plist/UID/UTF-8/ZIP budget、重复名、头不一致、Zip64 | 纯内存 fuzz/表驱动 |
| BackupBatch | 部分 PUT、manifest 发布、hash 失败、PROPFIND 多状态、配置撕裂 | fake WebDAV server |
| RenderGolden | DASH/DOTS/高亮/铅笔/变宽/transform/zoom/erase | 模拟器截图 + 像素差分 |
| LibraryStress | 100 笔记缩略图、快速切文件夹、删除/新建失败 | UI 自动化 |
| DeviceInk | MatePad 压感/倾角、端到端延迟 P50/P95、长写内存 | 目标真机 |

分层门槛：

1. 每批：`check_ets_files` 或等价静态诊断，涉及文件零错误。
2. 每批：`note@default` debug 构建成功。
3. 有测试的批次：证明 runner 实际执行并报告断言数，不能只证明 `ohosTest` HAP 编译。
4. 渲染/UI：至少 360×800、600×960、1280×800 三档截图。
5. 最终发布：模拟器冒烟 + 目标 MatePad 真机；WebDAV 用至少两种真实服务端。
6. 性能结论必须有设备、版本、样本数、P50/P95 和采集方法；禁止写“应该 <16ms”。

## 十六、指挥官验收 SOP

每个批次交付后，指挥官按以下顺序验收：

1. 读任务报告和 `git diff`，确认没有夹带跨批重构、没有覆盖并行修改。
2. 对照本文件逐条判定：通过、部分通过、返工、因证据不足挂起。
3. 运行涉及文件静态检查，再运行 `note@default` debug build。
4. 运行真实测试任务并记录断言数；不能运行时明确写“未执行”及阻塞原因。
5. 抽查 1-2 个关键符号和一个失败路径，不只看 happy path。
6. UI/渲染批次启动模拟器，保存三档截图；输入/性能最后上目标真机。
7. 数据库/导入批次必须用升级前数据和失败注入，不允许只测新安装。
8. 只有全部客观验收通过后才允许精确暂存和提交；工作区有并行修改时禁止目录级 `git add`。

最终发布门槛不是“147 条都打勾”，而是：数据不会因竞态丢失、输入样本不再被入口截断、渲染坐标只有一个定义、导入对损坏/敌意包可控、备份能恢复完整批次、核心编辑操作可逆、手机和平板主要功能均可达。
