## 零、先说结论

已落盘 147 条缺陷，每条都有出处与验收标准，**可以直接派工**。但覆盖度是不均匀的：

| 覆盖状态 | 文件数 | 说明 |
|---|---:|---|
| ✅ 逐行审，且有原版基准闭环 | 8 | 主要是算法层与数据层核心 |
| 🟡 逐行审，但基准侧有缺口 | 14 | 移植侧自洽性已查，与原版是否一致未验证 |
| ⚠️ 主干覆盖，非逐行 | 6 | 含三个最大的文件 |
| ❌ 完全未审 | 12 | 见第一节 |

**最需要警惕的一句话**：域4（渲染与编辑器，40 条缺陷，占总量 27%）**几乎全部是移植侧自洽性推演，不是与原版的行为比对**。也就是说"跟原版一不一样"这件事，在最容易出问题的模块上基本没做过。

## 一、完全未审的文件（12 个）

按风险排序。前四个建议下一轮优先补。

### 1. `core/adaptation/Canvas2DStrokeRenderer.ets`（462 行）— **最大缺口**

域1 覆盖度声明中已明确标注 ❌ 未审。这是**所有笔画的最终落笔处**：颜色、混合模式、线帽线连接、荧光笔透明度、虚线参数、splat 绘制全在这里。

已知线索（来自 `reports/T-040-AUDIT-完成.md` 自己记录的待办）：

> dash 参数（2w/1w、0.001w/2w）未对照 1.0.3 pzf 对应物；highlighter 用 alpha 0.42 简化（原版 BlendMode）

即荧光笔当前是**用 alpha 近似替代原版的混合模式**，虚线参数无基准。这两条都直接影响观感，且都还没被正式登记为缺陷条目。

基准：1.0.1 `defpackage/pzf.java`（10045 字节，已在 `reference/defpackage/` 中）。

### 2. `ui/editor/EditorToolbar.ets`（127 行）

全库仅 1 次引用，属偶然提及。工具切换、笔宽/颜色选择、当前工具态的单一真相源都在这里。域5 发现的 U-04（改 ViewModel 内部字段不触发刷新）是同类问题的典型，工具栏极可能有相同病症。

### 3. `ui/editor/EditorViewModel.ets`（53 行）

4 次引用均为顺带。它是编辑器的状态中枢，`@Observed` 用法是否正确直接决定工具栏与画布的联动是否生效。

### 4. `ui/editor/PageManagerBar.ets`（112 行）

8 次引用，但只有 R-26（pages 为空时传 `undefined`）是针对它的。翻页、加页、删页的交互入口在此，而 R-31 已确认**页级操作完全不可撤销**——这个文件是那条缺陷的现场。

## 三、基准侧的缺口（"对照原版"这件事没做完的部分）

这是比"文件没审"更值得关注的一类——文件审了，但**没有拿原版比对**，所以只能发现"自相矛盾"，发现不了"和原版不一样"。

### 3.1 域4 整体：几乎没有与原版对照

域4 覆盖度声明原文：

> `androidx/ink/**` 与 `com/gingerlabs/notability/feature/note/` **未做系统性对照**。域4 绝大多数条目是移植侧的自洽性推演（坐标系、生命周期、状态管理），而非与原版的行为差异比对。

40 条缺陷里，坐标系、Undo 对称性、脏矩形这些都是"移植侧自己前后矛盾"。而诸如"原版橡皮擦到底是什么语义""原版选区变换后笔宽怎么处理""原版的视口缩放锚点在哪"——这些**只能靠对照原版才能回答的问题，一个都没回答**。

建议单开一张任务卡：以 `androidx/ink/strokes/` + `androidx/ink/geometry/` + `feature/note/` 为基准，做一轮渲染与交互行为对照。

### 3.2 域2：原版 Room schema 未逐表比对

D-01（无页维度）、D-02（op-log 退化）、D-05（缺外键）三条 P0/P1 的基准证据都是 🟡（结构性推断），依据是包路径命名与异常类名，**没有真的把原版 `*Database_Impl.java` 里的建表 SQL 拉出来逐列对比**。

原版有六个 Room 库：`NoteStateDatabase` / `NoteAssetDatabase` / `NoteBundleMetadataDatabase` / `RawLibraryStateDatabase` / `ToolboxDatabase` / `SettingsDatabase`，外加 `LearnDatabase` / `SearchDatabase` / `TranscriptionDatabase`。`*Database_Impl.java` 是 Room 生成的，含完整 DDL——这是**整个项目里最硬、最容易拿到的基准证据**，却还没用。

建议：这是投入产出比最高的一张补审卡。

### 3.3 三个混淆类未定位（阻塞三条具体修复）

| 待定位 | 阻塞的条目 | 需要产出 |
|---|---|---|
| `fc0` 的实现类 | A-15（angleDiff 该用哪个字段）、A-17（散布方向向量来源） | 该类的字段定义与 `a()~e()` 的返回值语义 |
| `f92.c(...)` | A-19（opacity 最终钳制是否为纯 clamp） | 方法体 |
| `dd4.d()` | A-07（动态容差公式的四个常数与 log 底数） | `sqh.f` 调用点的第二参表达式 |
| 原版 undo 栈深度 | R-32（移植侧 50 是拍脑袋值） | `feature/note/` 下撤销管理器的上限常量 |

这四条都是**小任务**（各半小时内可闭环），但不做就只能一直挂 ❓。

### 3.4 `.note` 格式：结构性无基准

域3 已确认：**Android 原版不读 iPad 的 `.note` 归档格式**，反编译源中没有对应解析代码。所以 `NotabilitySessionParser` / `BinaryPlistParser` / `NSKeyedArchiverDecoder` 三个文件（合计 1933 行）的基准只能是「真实样本字节 + CFBinaryPlist/PKZIP 规范」，**永远不会有原版代码可对照**。

这不是缺口，是客观限制，但要在心里记明白：这块的正确性只能靠样本回归测试保障，不能靠对照。

## 五、验证手段的缺口

当前**全部 147 条的验收标准都是静态可判定的**（grep / 代码走查 / 纯内存单测），零运行态验证。这是用户当前条件下的正确选择，但要清楚它挡不住什么：

- 挡不住"改完编译不过"——需要 `check_ets_files` + `build_project`
- 挡不住"逻辑对了但观感不对"——尤其 FIX-D（坐标系）、FIX-J（铅笔）这两批，改完必须看画面
- 挡不住"多页/大数据量下才暴露的问题"

已知需要外部条件才能闭环的项：

| 项 | 需要什么 | 阻塞的条目 |
|---|---|---|
| 压感往返保真 | 一份**带 Apple Pencil 压感**的 `.note` 样本（现有 OP-AMP.note 压感恒 1.0） | F-19 |
| 备份恢复 | 真实 WebDAV 服务器 | FIX-B 整批的端到端验证 |
| 压感曲线调参 | 目标 MatePad 真机 | 交接文档遗留清单 |
| 端到端延迟 P50/P95 | 目标 MatePad 真机 | 同上（目标 <16ms，不得预设达成） |
| PencilSplat 散布观感 | 真机 + 有倾角数据的手写笔 | A-16/A-18 修复后的复验 |

## 六、指挥官建议的补审优先级

若要在派工前再补一轮审计，按这个顺序投入产出比最高：

1. **原版 Room schema 逐表比对**（3.2）——最硬的证据、最容易拿、能把三条 P0/P1 从 🟡 提到 ✅
2. **`Canvas2DStrokeRenderer.ets`**（1.1）——462 行完全空白，且已知有两处待办线索
3. **三个混淆类定位**（3.3）——四个小任务，解锁四条挂起的条目
4. **`EditorToolbar` + `EditorViewModel` + `PageManagerBar`**（1.2~1.4）——共 292 行，且与已确认的 U-04、R-31 直接相关
5. **域4 与 androidx.ink 的系统性对照**（3.1）——工作量最大，但这是"移植保真度"的核心问题

**但也可以不补。** 147 条已足够支撑两三个月的修复工作，且很多未审区域的问题会在修复过程中自然暴露。**边修边补审通常比先审全再动手更划算**——尤其 FIX-A（存储页维度）和 FIX-D（坐标系）落地后，对代码的理解会显著加深，那时再回头审剩余文件效率更高。

这个取舍请指挥官/用户定夺。
