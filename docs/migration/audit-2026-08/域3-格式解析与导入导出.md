## F-01 · P0 · 导出的 .note 无法被自己读回（往返彻底断链）

**位置**：`note/src/main/ets/data/ZipArchive.ets:234-235`（Local File Header）、`:255-256`（Central Directory）

**现状代码**
```
localWriter.writeU32(p.data.length);            // compressed size
localWriter.writeU32(p.data.length);            // uncompressed size   ← 写的还是压缩后长度
...
cdWriter.writeU32(p.data.length);               // compressed size
cdWriter.writeU32(p.data.length);               // uncompressed size   ← 同上
```
`p.data` 在 `ZipArchive.ets:200-204` 已被替换为 deflate 后的负载：
```
const deflated: Uint8Array = await deflateRaw(raw);
if (deflated.length < raw.length) { payload = deflated; method = METHOD_DEFLATE; ... }
```

**基准证据** ✅
PKZIP APPNOTE 4.3.7/4.3.12：LFH 偏移 +18 为 compressed size、+22 为 **uncompressed size**；
CD 偏移 +20/+24 同理，二者语义不同。
真实样本 `OP-AMP.note` 全部条目为 STORE，两值相等因而看不出问题：
```
OP-AMP/Session.plist  method=0  file_size=558797  compress_size=558797  flag=0x800
OP-AMP/metadata.plist method=0  file_size=955     compress_size=955     flag=0x800
```
即：**样本无法掩盖该 bug，因为样本根本没用 deflate**；而移植侧 `NoteExporter.ets:84,96`
对 manifest.json 与每个 page_N.json 都传 `compress=true`，>64 字节即走 deflate。

**差异描述**
自家导出的 .note 一旦命中 deflate（正常笔记必然命中），头部记录的 uncompressed size 是错的。
回读时 `ZipArchive.ets:317` 读出的 `usize` 实为压缩长度，接着：
- `:339` `inflateRaw(compressedData, usize)` → 输出缓冲上界 `max(usize,1024)` 远小于真实解压长度 → 截断；
- `:340` `content.length !== usize` 恒不成立 → `return null`；
- `NoteImporter.ets:54-56` 收到 null → 返回 `CORRUPTED`「文件不是有效的 .note 包或已损坏」。

结论：**导出→导入 100% 失败**，且第三方解压工具同样会报尺寸/CRC 不符。
WebDAV 备份链路（`exportAllNotes`）产出的全部备份文件都是不可恢复的。

**修复指令**
1. `PreparedEntry` 增加 `rawSize: number` 字段，在 `:212-219` 构造时填 `raw.length`。
2. `:234-235` 改为 `writeU32(p.data.length)` + `writeU32(p.rawSize)`；`:255-256` 同样改。
3. 增加一条单元自检：`ZipWriter.build()` 产物立即喂给 `ZipReader.parse()`，逐条断言
   `entry.data` 与入参字节完全相等（含一条 >4KB 高压缩率文本条目）。

**验收标准**
- `ZipArchive.ets` 中 LFH 与 CD 的 uncompressed-size 写入位使用的是**未压缩前**长度变量，
  静态检查两处 `writeU32` 参数不再是同一表达式；
- 存在一个往返测试用例，输入含至少一条 `method=DEFLATE` 的条目且断言字节级相等；
- 用系统 `unzip -t` 校验导出的 .note 返回 `No errors detected`。

## F-02 · P1 · zlib 返回 `OK` 被当成功，压缩/解压静默截断

**位置**：`ZipArchive.ets:133`、`ZipArchive.ets:161`
```
status = await zip.deflate(strm, zlib.CompressFlushMode.FINISH);
...
if (status !== zlib.ReturnStatus.STREAM_END && status !== zlib.ReturnStatus.OK) { throw ... }
```

**基准证据** 🟡 zlib 契约：`deflate(..., Z_FINISH)` 仅在**全部输出已写出**时返回 `Z_STREAM_END`；
返回 `Z_OK` 表示 **输出缓冲不足、流未结束**。把 `OK` 放行等于接受一个被截断的 deflate 流。

**差异描述**
`:119` 的膨胀上界公式 `len + (len>>12)*5 + 64` 是 zlib `deflateBound` 的近似，
对已压缩数据（如笔记里内嵌的 PNG/JPEG base64、随机 ID 串）可能不够；一旦不够，
当前代码不报错，直接把半截压缩流写进 ZIP，产出一个 CRC 通不过的包。
inflate 侧同理：`outCap = max(expectedSize,1024)`，若 `expectedSize` 偏小则静默截断
（F-01 修复后由长度校验兜住，但 `deflate` 侧无任何兜底）。

**修复指令**
- 两处均改为**只接受 `STREAM_END`**；收到 `OK` 时按缓冲不足处理：
  deflate 侧扩容重试（`outCap *= 2`，上限 3 次），仍失败则回退 STORE；
  inflate 侧扩容重试，仍失败则整条目判损坏。
- `deflateRaw` 结束后追加断言 `strm.availableIn === 0`。

**验收标准**：`ZipArchive.ets` 中不存在 `status !== ...STREAM_END && status !== ...OK` 这一放行形式；
`deflateRaw` 内出现扩容重试循环或回退 STORE 的分支。

## F-03 · P1 · 单条目损坏即整包放弃，无部分导入

**位置**：`ZipArchive.ets:304, 311-312, 324-325, 331-332, 343-345, 348-350`（六处 `return null`）
与 `NoteImporter.ets:53-57`

**基准证据** ✅ 原版存在专门的部分成功语义：
`decompiled_1.0.3/sources/com/gingerlabs/notability/ui/fileimport/data/importer/PartialImportException.java`
```java
public PartialImportException(List list, Throwable th) {
    super(fa2.i(list.size(), "Import partially succeeded: ", " notes created"), th);
    this.I = list;
}
```
以及 `data/library/state/ntb/MissingAssetsException.java`
```java
super(fa2.i(arrayList.size(), "Cannot export note: ", " asset(s) not downloaded locally"));
```
即原版把"部分成功 + 缺失资产清单"当作一等公民向上抛，而不是二值成败。

**差异描述**
移植侧 `ZipReader.parse` 是全有全无：某个 `thumb12x.png` CRC 不符、或出现一条
`method=12(bzip2)` 的无关条目，就导致整篇笔记（笔迹完好）被判 `CORRUPTED`。
`ImportResult.PARTIAL` 枚举已存在（`NoteImporter.ets:26`），但 ZIP 层根本不给它机会。

**修复指令**
1. `ZipReader.parse` 返回 `{ entries: ZipEntry[], failed: string[] }`：
   条目级失败（CRC 不符 / 不支持的 method / 越界）记入 `failed` 并 `continue`，
   仅在 EOCD 缺失或 CD 完全不可遍历时才整体返回 null。
2. `NoteImporter.importFromData` 把 `failed` 并入 `caveats`，
   若关键条目（manifest.json / Session.plist）在 failed 中才判 `CORRUPTED`，
   否则判 `PARTIAL` 并在 message 中列出损坏条目名。

**验收标准**：`ZipReader.parse` 签名不再是 `Promise<ZipEntry[] | null>`；
逐条目 `catch/continue` 存在；`NoteImporter` 中出现对损坏条目清单的消费点。

## F-04 · P1 · NSKeyedArchiver 的 nil（UID 0）被当成字符串 `"$null"`

**位置**：`NSKeyedArchiverDecoder.ets:343-355`
```
resolve(value: PlistValue | null): PlistValue | null {
  if (value.type !== PlistType.UID) { return value; }
  const idx: number = value.asUid();
  if (idx < 0 || idx >= this.objects.length) { return null; }
  return this.objects[idx];        // ← idx===0 时返回 $objects[0]，即字符串 "$null"
}
```

**基准证据** ✅ 真实样本 `OP-AMP/metadata.plist` 的 `$objects[0]`：
```
archiver NSKeyedArchiver  top {'root': UID(1)}
obj0  str  '$null'
```
NSKeyedArchiver 规范：`$objects[0]` 恒为占位串 `"$null"`，**任何指向 UID 0 的字段都表示 nil**。

**差异描述**
`stringOf()`（`:138-160`）与 `asText()`（`:163-181`）在字段为 nil 时会返回字符串 `"$null"`
而非 fallback。直接受害者：
- `NotabilitySessionParser.ets:181-183` → `noteName` / `uuid` / `subject`
- `:230,233,234` → 会话名、bundleVersion、handwritingLanguage
- `:241-245` → paperSize / paperOrientation / lineStyle2

后果链：`NoteImporter.ets:285-291` 判 `title.length === 0` 才回退，`"$null"` 长度非零，
于是**标题变成字面量 `$null`** 落库；`notabilityPaperSize("$null")` 走 default → LETTER，
`notabilityPaperTemplate("$null")` → PLAIN，静默取错纸型。
本样本各字段恰好都非 nil（`noteName→UID16→'OP-AMP'`、`noteSubject→UID17→'unsortedNotesKey'`、
`noteTags→UID15→''`），因此现有样本掩盖了该缺陷；无标题/无学科的笔记必然踩中。

**修复指令**
在 `resolve()` 内最前面加 nil 判定：
```
if (value.type === PlistType.UID && value.asUid() === 0) { return null; }
```
并在 `NSKeyedArchiverDecoder.decode()` 中校验 `$objects[0]` 确为字符串 `"$null"`，
不符则记 warning（防御非标准归档）。

**验收标准**：`resolve()` 中存在 `asUid() === 0 → return null` 分支；
`stringOf` / `asText` / `dataOf` / `numberOf` / `dateMillisOf` 在字段指向 UID 0 时均走 fallback 路径。

## F-05 · P1 · 往返丢失 noteId / createdAt / updatedAt

**位置**：`NoteImporter.ets:143-144`
```
const title: string = manifest.title !== null && manifest.title.length > 0 ? manifest.title : '导入笔记';
const note: NoteMeta = await noteRepo.createNote(title, null);

**基准证据** 🟡 移植侧自有格式契约 `NotePackageSpec.ets:11-21` 明确导出了

## F-06 · P1 · 横向页往返退化为纵向尺寸

**位置**：`NoteImporter.ets:155-163`（我方格式）与 `NoteImporter.ets:299-306`（Notability）
```
const mm: number[] = paperSizeToMm(page.paperSize as PaperSize);
const pageInfo: PageInfo = { ..., orientation: page.orientation as PageOrientation,
  widthMm: mm[0], heightMm: mm[1] };     // ← 不论 orientation 一律 [短边, 长边]
```

**基准证据** ✅ 同工程内的权威写法 `ui/components/PageSettingsPanel.ets:47-52`：
```
if (updated.orientation === PageOrientation.LANDSCAPE) {
  updated.widthMm = dims[1];
  updated.heightMm = dims[0];
} else { updated.widthMm = dims[0]; updated.heightMm = dims[1]; }
```
即"横向要交换 mm"是本工程既定不变量，导入路径违反了它。
`NoteExporter.ets:88-96` 又根本不导出 `widthMm/heightMm`，所以无法靠原值兜回来。

**差异描述**
导出→导入后，横向 A4 页的 `widthMm=210 / heightMm=297`，但 `orientation=LANDSCAPE`。
页面模型自相矛盾，格线绘制与纸张边框会按纵向尺寸渲染。
Notability 路径同样：`session.paper.paperOrientation === 'landscape'` 时
`:299` 仍取未交换的 mm。

**修复指令**
1. 把交换逻辑提取为 `NoteExporter.ets` 的导出函数
   `export function paperSizeToMmOriented(size: PaperSize, o: PageOrientation): number[]`，
   `PageSettingsPanel` 与两条导入路径统一调用。
2. `NotePackageSpec.PageData` 增补可选 `widthMm/heightMm`，导出时写入、导入时优先采用，
   缺失才回退按 size+orientation 推导（兼容旧包）。

**验收标准**：`NoteImporter.ets` 中不再直接调用 `paperSizeToMm(...)` 后无条件取 `mm[0]/mm[1]`；
grep `paperSizeToMm(` 的全部调用点均带 orientation 参数或后接交换分支。

## F-07 · P1 · 元素-页归属在往返中彻底丢失

**位置**：`NoteExporter.ets:86-97`
```
elements: i === 0 ? elementObjects : [],   // 第 0 页带全部元素，其余页空
```
与 `NoteImporter.ets:166-178`
```
for (const el of page.elements) { ...allStrokes.push(...) }   // 各页元素合并进同一个数组
...
await this.persistence.saveElements(note.id, allStrokes, allTexts);
```

**基准证据** ⚠️ 源自 `StrokePersistence` 按 noteId 整存整取、无页维度（代码注释
`NoteImporter.ets:357-359` 自述）。这是既有存储层限制，但**导出格式已经定义了页维度**
（`NotePackageSpec.PageData.elements`），导出端主动把它作废了。

**差异描述**
`page_0.json` 承载全部元素，`page_1..N.json` 恒为空数组。这不是"暂不支持"，而是**写出了错误信息**：
接收方（包括未来修好页维度的自己、以及任何第三方）会认为该笔记的内容确实全在第 1 页。
一旦 T-041 补上页维度，历史导出的所有备份都无法正确还原分页。

**修复指令**（存储层未改前也可先做，成本低）
1. `NoteExporter` 在 manifest 增加 `"pageAssociation": "none"` 标记，
   显式声明本包的元素-页归属不可信；导入端读到该标记时才走"全部合并"路径。
2. 或（更优）：导出时按 `StrokeElementData.bounds.top / pageHeight` 反推页号写入对应 page_N.json，
   导入时按页还原偏移——与 `NoteImporter.flattenPages`（:360-369）的纵向拼接互为逆运算。

**验收标准**：`NoteExporter.exportNote` 中不再存在 `i === 0 ? elementObjects : []` 这一表达式；
或 manifest 中存在显式的归属声明字段，且 `NoteImporter` 对该字段有分支消费。

## F-08 · P2 · 不支持 Zip64

**位置**：`ZipArchive.ets:301-306`（EOCD 字段直接当真值用）、`:315-321`、`findEocd :372-385`

**基准证据** 🟡 APPNOTE 4.3.14/4.3.15：当条目数 >65535 或尺寸/偏移 >4GB 时，
EOCD 对应字段填 `0xFFFF/0xFFFFFFFF` 哨兵，真值在 Zip64 EOCD Record + Locator 中。

**差异描述**
`entryCount = readU16(eocd+10)`、`cdOffset = readU32(eocd+16)` 直接使用；
遇到 Zip64 包时 `cdOffset = 0xFFFFFFFF`，`:304` 判 `cdOffset + cdSize > data.length` → `return null`，
整包判损坏。带大量高清图片/PDF 底稿的 Notability 笔记（>4GB 罕见，但 >65535 条目在
逐笔画存图的包里并非不可能）会直接导入失败。写入端 `ZipWriter` 同样无 Zip64 输出能力。

**修复指令**
读取端：`findEocd` 之后向前 20 字节找 `0x07064b50`（Zip64 EOCD Locator），
据此定位 `0x06064b50` 记录，覆盖 entryCount/cdSize/cdOffset；
CD 条目中遇 `0xFFFFFFFF` 的 csize/usize/localOffset 时从 extra field id=0x0001 取真值
（当前 `:319 extraLen` 只用于跳过，需改为解析）。
写入端：条目数 >65534 或任一尺寸 >0xFFFFFFFE 时输出 Zip64 结构，否则维持现状。

**验收标准**：`ZipArchive.ets` 中出现常量 `0x06064b50` 与 `0x07064b50`，
且存在对 extra field header id `0x0001` 的解析分支。

## F-09 · P2 · 通用位标志未判定：加密未拒绝、文件名编码未按标志分派

**位置**：`ZipArchive.ets:314-322`（CD 解析处未读取 offset+8 的 general purpose flag）

**基准证据** ✅ 真实样本全部条目 `flag_bits=0x800`，即 bit 11(UTF-8) 置位：
```
OP-AMP/Session.plist  ... 0x800
OP-AMP/metadata.plist ... 0x800
```
APPNOTE 4.4.4：bit 0 = 加密；bit 3 = 用 data descriptor（尺寸/CRC 在数据之后）；
bit 11 = 文件名/注释为 UTF-8，未置位时应按 CP437 解码。

**差异描述**
1. `decodeUtf8(data, pos+46, nameLen)`（`:322`）无条件按 UTF-8 解；Windows 工具产出的
   非 UTF-8 中文名 ZIP 会得到乱码条目名，`findEntryBySuffix`（`NoteImporter.ets:348`）随之失配，
   笔记内容找不到 → 判 `UNSUPPORTED_FORMAT`。
2. bit 0 加密条目不被识别，会被当作正常压缩数据 inflate，失败后 `return null`，
   错误信息误导为"文件已损坏"而非"文件受密码保护"。
3. bit 3（data descriptor）：本实现走 CD 取尺寸，逻辑上正确（注释 `:5` 自述如此），
   **但这条正确性依赖 F-01 修复后 CD 尺寸真实**，需在修复中一并保住。

**修复指令**
- 读取 `flags = readU16(data, pos + 8)`；
- `(flags & 0x01) !== 0` → 该条目标记为加密，走 F-03 的条目级失败路径并给出"受密码保护"提示；
- `(flags & 0x0800) === 0` → 文件名按 CP437 映射表解码（可内置 128-255 映射数组）。

**验收标准**：`ZipArchive.ets` CD 解析处出现 `readU16(data, pos + 8)` 且有基于 bit0 / bit11 的分支。

## F-11 · P2 · plist 对象区上界取错，可越界读进偏移表

**位置**：`BinaryPlistParser.ets:301`
```
const ctx = new ParseContext(data, offsets, objectRefSize, t);   // t = data.length - 32
```
`limit` 在 `:360` 用作对象偏移的唯一上界。

**基准证据** ✅ 样本 Session.plist trailer：
```
trailer 00000000 00 00 04 02 0000000000000134 0000000000000000 00000000000881dd
offsetIntSize=4  objectRefSize=2  numObjects=0x134(308)  topIndex=0  offsetTableOffset=0x881DD(557533)
文件长度 558797 → t = 558765；557533 + 308*4 = 558765

**修复指令**：`ParseContext` 的 `limit` 传 `offsetTableOffset`；
同时保留 `offsetTableOffset <= t` 的既有校验。

**验收标准**：`BinaryPlistParser.ets:301` 处 `new ParseContext(...)` 第四参为 `offsetTableOffset`。

## F-12 · P2 · 8 字节整数精度与符号处理

**位置**：`BinaryPlistParser.ets:26-32`（`uintBE` 浮点累乘）与 `:392-396`
```
let v: number = uintBE(this.data, pos + 1, size);
if (size === 8 && (this.data[pos + 1] & 0x80) !== 0) { v = v - Math.pow(2, 64); }
```
函数头注释自述"size ≤ 6 时精确"，却在 size=8 时被调用。

**差异描述**
|value| > 2^53 时 `uintBE` 已丢低位，再减 2^64 得到的负数误差可达数千。
影响面：`trailer` 的 numObjects/topIndex/offsetTableOffset（`:278-280`，
实际文件不会超 2^53，风险低）与 plist 中的 64 位整型字段
（Notability 的 `options` 数组是 NSData 不走这里；但 `curveUUIDs` 之外的
未来 u64 字段一旦出现即受影响）。

**修复指令**：`uintBE` 对 size===8 走高低 32 位分离：
`hi*2^32 + lo`，并在 `hi > 0x1FFFFF` 时返回 `Number.MAX_SAFE_INTEGER` 同时置 ctx.error 或 warning；
负数转换改为 `(hi - 0x100000000) * 0x100000000 + lo`。

**验收标准**：`uintBE` 或新增的 `int64BE` 中出现高低 32 位分离计算，且函数头注释的
"size ≤ 6 时精确" 限制不再与调用点冲突。

## F-13 · P2 · plist marker 覆盖不全

**位置**：`BinaryPlistParser.ets:368-529` 的 `switch (high)`

**已覆盖**：0x0(null/bool/fill)、0x1(int)、0x2(real)、0x3(date)、0x4(data)、
0x5(ASCII)、0x6(UTF-16BE)、0x8(UID)、0xA(array)、0xC(set)、0xD(dict) ✅

**缺失** 🟡（对照 CoreFoundation `CFBinaryPList.c` 的 marker 表）：
- `0xB` = **NSOrderedSet**（CFBinaryPlist v0 中 0xA=array、0xB=ordset、0xC=set）。
  当前 `case 0xA: case 0xC:` 并列处理，0xB 落进 `default` → 报"未知对象标记"，整份 plist 解析失败。
- `0x0` 系的 `0x0C`/`0x0D`/`0x0E`（CFBinaryPlist v1x/v2 的 null/URL-with-base/UUID）→
  `:382` 报错返回 null。
- ASCII 分支（`:447-451`）不校验字节 >0x7F，非法 ASCII 会被静默当 Latin-1 收下（P3 级）。

**修复指令**：`case 0xB` 并入 0xA/0xC 分支（新增 `PlistType.ORDSET` 或复用 ARRAY）；
`0x0` 系补 `0x0C→null`、`0x0D→(URL, 后跟一个 string 对象)`、`0x0E→(UUID, 16 字节)`，
最低限度是"识别并跳过而不整体失败"。

**验收标准**：`switch (high)` 中存在 `case 0xB`；`case 0x0` 的 low 分支覆盖 0xC/0xD/0xE。
