## R-01 【P0】纸张原点随 zoom 漂移 → 缩放后所有已有笔画相对纸张整体错位

- 位置：`note/src/main/ets/ui/editor/NoteCanvasView.ets:183-185`、`note/src/main/ets/rendering/PaperRenderer.ets:20-25`、`NoteCanvasView.ets:1009-1016`
- 证据 ✅：

`renderFrame()` 把**视口的画布空间尺寸**当作纸张定位基准传给 PaperRenderer：

```
this.paperRenderer.renderBackground(this.canvasCtx, w / this.viewport.zoom,
  h / this.viewport.zoom, ..., this.currentPage.widthMm, this.currentPage.heightMm);
```

PaperRenderer 里：

```
paperW = paperWidthMm * 3.78;
paperX = Math.max(0, (width - paperW) / 2);   // width === w / zoom
```

即纸张在**画布坐标系**中的原点 `paperX = (w/zoom - paperW)/2`，是 zoom 的函数。
而笔画点 (`completedStrokes[].pathPoints`) 存的是**画布坐标绝对值**，与 zoom 无关。

推演：设 w=1000、paperW=794（A4）。
- zoom=1 → paperX=(1000-794)/2=103
- zoom=2 → paperX=max(0,(500-794)/2)=0
- zoom=0.5 → paperX=(2000-794)/2=603

同一笔画（画布 x=150）在 zoom=1 时位于纸内左边距 47，在 zoom=0.5 时跑到纸张左边界**外**（150 < 603）。

- 用户可见现象：缩放（捏合 / +− 按钮 / 适应宽度）后，纸张背景与线格相对笔迹整体平移；笔迹会跑到纸外或叠到边缘；重开笔记（恢复 zoom）后位置又变一次。这是"页面/笔迹对不齐"类反馈的根因。
- 关联同源错误：`toRawPointerEvent()`（NoteCanvasView.ets:1009-1016）用同一公式做**输入裁剪**，所以不同 zoom 下笔画能画到的合法区域也在变；`zoomFitWidth()`（:251-256）同样用 `vw = w/clamped` 推 paperX，与之相互抵消，掩盖了部分症状但没有消除根因。
- 修复指令：纸张原点必须是**与视口无关的常量**（页面坐标系原点）。
  1. 在 `CanvasViewport` 或页面模型中定义 `paperOrigin = {x:0, y:0}`，纸张矩形恒为 `(0,0,paperW,paperH)`，笔画坐标即页面坐标。
  2. `PaperRenderer.renderBackground` 改为接收 `paperX/paperY/paperW/paperH` 显式参数，**不再**从 width/height 推导居中。
  3. "居中"改由视口负责：`renderFrame` 前调用 `viewport.centerPaper(canvasW, canvasH, paperW, paperH)` 调整 scrollX/scrollY，而非移动纸张。
  4. `toRawPointerEvent` 的裁剪改为 `clamp(p, 0..paperW, 0..paperH)`。
- 验收（静态）：全仓 grep `(width - paperW) / 2` 与 `(vw - pw) / 2` 结果为 0；`PaperRenderer.renderBackground` 签名不含从 width 推 paperX 的分支；`toRawPointerEvent` 中不出现 `this.viewport.zoom`。

## R-02 【P1】选区拖拽命中判定：画布坐标 vs 屏幕坐标混用

- 位置：`NoteCanvasView.ets:315`（判定） vs `NoteCanvasView.ets:762-765`（赋值）
- 证据 ✅：

`updateSelectionOverlay()` 明确把 selectionRect 存为**屏幕坐标**：

```
const tl: Point2D = this.viewport.canvasToScreen(rect.left, rect.top);
const br: Point2D = this.viewport.canvasToScreen(rect.right, rect.bottom);
this.selectionRect = { left: tl.x, top: tl.y, right: br.x, bottom: br.y };
```

而 onTouchDown 用**画布坐标**去比：

```
if (this.selectionVisible && this.pointInRect(canvasP, this.selectionRect)) {
```

- 用户可见现象：zoom≠1 或已平移时，按住选区内部不会进入拖拽，而是重新开一个新选区（选中的内容被"取消"）；反之在选区外某处按下却触发了拖拽。zoom=1 且 scroll=0 时恰好正确，所以模拟器默认状态测不出来。
- 修复指令：另存一份画布坐标的 `selectionRectCanvas`（用于命中判定），`selectionRect` 仅供 Overlay 显示；`pointInRect(canvasP, this.selectionRectCanvas)`。
- 验收（静态）：`pointInRect` 的两个入参坐标系在注释中标注一致；`selectionRect` 的所有读点仅出现在 build() / SelectionOverlay 传参与 `isInSelectionMenu`（均为屏幕坐标）。

## R-03 【P1】选区拖拽期间变换矩阵重复累积 → 拖动位移被指数放大

- 位置：`NoteCanvasView.ets:370-378`、`SelectionTool.ets:86-90`、`SelectionTool.ets:117-138`
- 证据 ✅ + 🟡（纯逻辑推演，确定性）：

每个 move 事件：
```
this.selectionTool.moveSelected(dx, dy);        // state.transform = T_new = t_i · T_{i-1}
this.applySelectionTransform(false, false);     // strokes.transform = T_new · strokes.transform
```
而 `applyTransform` 的输入是**上一帧已经写回 transform 的 strokes**（`this.completedStrokes` 被就地覆盖，见 :772）。

推演三帧（每帧位移 d）：
- 帧1：T=t1，笔画 = t1·S
- 帧2：T=t2·t1（累计位移 2d），笔画 = (t2·t1)·(t1·S) → 累计位移 **3d**
- 帧3：T=t3·t2·t1（3d），笔画 = 3d·3d… → 累计 **6d**

位移序列 1d,3d,6d,10d…（三角数），拖动 10 帧就偏出 55 倍。

- 用户可见现象：拖动选中笔迹时，笔迹"飞出去"，远远快于手指、瞬间离开屏幕。这是选区功能几乎不可用的直接原因。
- 修复指令：二选一，推荐 (a)。
  - (a) 每帧从**原始快照**重算：`this.completedStrokes = this.selectionTool.applyTransform(this.dragBeforeStrokes)`，即 applyTransform 的输入永远是拖拽开始时的快照。
  - (b) 每帧只把**增量** t_i 应用到当前 strokes，且 `state.transform` 不累积（拖拽结束再用累计矩阵记 undo）。
- 验收（静态）：`applySelectionTransform` 内不再出现 `applyTransform(this.completedStrokes)` 这种"自输入自输出"写法；或 `moveSelected` 在拖拽路径中不再 multiply 累积。

## R-04 【P1】选区变换会等比缩放 bounds 但不缩放笔宽 / 且缩放-旋转后笔宽表现不一致

- 位置：`SelectionTool.ets:122-132`
- 证据 ✅：`applyTransform` 只改 `transform` 与 `bounds`，`renderSpec`（含笔宽）原样保留。
- 用户可见现象：对选区做缩放（`scaleSelected`）后，笔迹几何被放大但线条粗细不变 → 放大后线显得过细、缩小后过粗，与原版 Notability 行为不符（原版 `androidx.ink` 的 `Stroke` 变换会同步 brush size，见 `androidx/ink/strokes/`）。
- 备注 ❓：当前 UI 只暴露了移动 / 翻转 / 层序，`scaleSelected` / `rotateSelected` 尚无入口（grep 无调用点），所以现阶段不可感知；一旦接入手柄缩放即暴露。
- 修复指令：`applyTransform` 中依据矩阵的平均线性尺度 `s = sqrt(|det(M2x2)|)` 同步缩放 `renderSpec.strokeWidth`（并对 splat 半径同处理）；翻转（det<0）取绝对值避免负宽。
- 验收（静态）：`applyTransform` 中出现基于 `m[0]*m[4]-m[1]*m[3]` 的尺度计算并写入新的 renderSpec。

## R-05 【P1】一次擦除动作压入两条 undo 记录 → 撤销一次只还原一半

- 位置：`NoteCanvasView.ets:564-594`
- 证据 ✅：`applyEraser()` 中先 push `ERASE_STROKES`（整笔删除部分），随后又 push `TRANSFORM_STROKES`（PARTIAL 挖洞部分）。当一次擦除同时命中"删除若干笔 + 部分挖洞若干笔"时，栈里是两条独立记录。
- 用户可见现象：擦一下要点两次撤销才回到原样；点一次撤销后画面处于"半还原"中间态（被删的笔回来了但挖洞还在，或反之）。redo 同理需点两次。
- 修复指令：给 `UndoableAction` 增加复合类型（如 `COMPOSITE` + `children: UndoableAction[]`），或让 UndoRedoManager 支持 `beginGroup()/endGroup()` 事务；`applyEraser` 一次擦除只产生一个栈项。
- 验收（静态）：`applyEraser` 中 `this.undoRedo.push(` 出现次数 ≤ 1（或包裹在 begin/endGroup 内）。

## R-06 【P1】复制（COPY）：副本与原件完全重合，且不可撤销、不持久化 undo 状态

- 位置：`NoteCanvasView.ets:889-923`
- 证据 ✅：`cloneStroke` 只把 **bounds** 平移了 +20，`pathPoints` / `cubicSegments` / `splatPoints` 是 `slice()` 浅拷贝且**坐标未平移**：

```
pathPoints: s.pathPoints.slice(),
...
bounds: { left: s.bounds.left + 20, top: s.bounds.top + 20, ... },
```

`copySelected` 之后也**没有 push 任何 undo**（:896-901 只有 rebuild/persist/renderFrame）。

- 用户可见现象：点"复制"后画面看不出变化（副本精确压在原件上，仅颜色略深），用户会连点多次；之后无法撤销这些副本；文件体积悄悄膨胀。选区框位置（按 bounds 算）与实际笔迹错开 20px。
- 修复指令：
  1. 复制时对每个 `pathPoint.position`、`cubicSegments`、`splatPoints` 全部平移 (+20,+20)，或改为在 `transform` 上乘一个平移矩阵并同步 bounds（两者取其一，禁止只改 bounds）。
  2. `pathPoints.slice()` 是浅拷贝，元素对象仍共享——需深拷贝，否则后续对副本的变换会污染原件。
  3. push 一条 `ADD_STROKE`/复合 undo 记录，并 `notifyUndoRedo()`。
- 验收（静态）：`cloneStroke` 中出现对 `position` 的坐标运算；`copySelected` 中出现 `this.undoRedo.push(` 与 `this.notifyUndoRedo()`。

## R-07 【P0】已完成笔画层是屏幕尺寸位图，却在视口变换内绘制 → 缩放后笔迹模糊 + 画布外笔迹永久丢失

- 位置：`NoteCanvasView.ets:171-193`、`rendering/StrokeLayerManager.ets:25-32, 73-85, 97-106`
- 证据 ✅：

`layerManager.initialize(w, h)`（NoteCanvasView.ets:160）用**屏幕像素**尺寸建 OffscreenCanvas；
`rebuildFromStrokes` / `commitStroke` 把笔画以**页面坐标原值**画进这张 w×h 的位图（`renderStrokeOnto` 只 setTransform(stroke.transform)，没有视口变换）；
而 `renderFrame` 在 `translate(scrollX,scrollY); scale(zoom,zoom)` **之后**才调用：

```
this.layerManager.compositeFull(this.canvasCtx, current, this.renderCtx);
```
compositeFull 内部：`mainCtx.drawImage(bmp, 0, 0, this.canvasWidth, this.canvasHeight);`

推演出的三个后果：
1. **裁剪丢失**：页面坐标超出 [0,w]×[0,h] 的笔画（A4 纸高 1123px > 屏幕高；或缩小到 0.25 后可视区域 4 倍大）在写入离屏层时就被裁掉，**再也画不出来**。缩小查看 / 滚动到页面下半部分时笔迹凭空消失。
2. **缩放模糊**：放大时是把一张屏幕分辨率的位图放大 zoom 倍，笔迹变糊、锯齿明显，而不是矢量重绘。
3. 每帧 `transferToImageBitmap()` + 两次 `drawImage`（:76-79）回写，性能开销与 GC 压力显著。

- 用户可见现象：放大后笔迹发虚发糊；缩小或下滑后页面下半部分的笔迹不见了（但数据还在，重启并保持 zoom=1 又出现）。
- 修复指令：
  1. 离屏层尺寸必须覆盖**整页页面坐标空间**（paperW×paperH，可再乘一个设备像素比上限），而不是屏幕尺寸；`initialize` 参数改为纸张尺寸。
  2. 或者（更贴近原版 `androidx.ink` 的做法）：离屏层保持屏幕尺寸，但**离屏渲染时也套用同一视口变换**，且在 `onViewportChanged` 时整层 `rebuildFromStrokes` 重建。二选一，不能像现在这样一半带变换一半不带。
  3. `compositeFull` 的 `drawImage` 目标矩形必须与离屏层所处的坐标系一致。
- 验收（静态）：`layerManager.initialize(...)` 的实参不再是 `this.canvasCtx.width/height`；或 `renderStrokeOnto` 中出现视口 translate/scale，且 `onViewportChanged` 中调用 `rebuildFromStrokes`。

## R-08 【P0】橡皮擦碰撞判定用「整条擦除路径的包围盒」与笔画包围盒相交 → 大面积误删

- 位置：`rendering/EraserEngine.ets:37-49, 79-105`
- 证据 ✅：`intersectsBounds` 先把**整条** eraserPath 压成一个 AABB，再与 stroke.bounds 做矩形相交。既不是逐段线段—笔画的距离判定，也不是逐点判定。
- 推演：用户从屏幕左上擦到右下（一条对角线），eraserPath 的 AABB 就是整个屏幕 → **屏幕内所有笔画全部被删**。即使短擦一下，任何 bounds 与该小矩形相交的长笔画（比如一条横贯全页的下划线）也会整条消失。
- 用户可见现象：轻轻擦一下，一大片无关笔迹（甚至整页）被删除。这是用户反馈"橡皮擦太狠/误删"的直接根因。
- 对照原版 🟡：`androidx/ink/geometry/` 的相交判定是逐段 `Segment`/`PartitionedMesh` 级别，Notability 的 WHOLE 擦也是笔画几何级命中，不是 bbox-vs-bbox。
- 修复指令：
  1. 第一层用 AABB 只做**粗筛**（快速排除）。
  2. 第二层做精判：对 eraserPath 的每一段线段，与 stroke 的 `pathPoints` 折线做「线段-线段最短距离 ≤ eraserRadius + brushWidth/2」判定，任一命中才算命中。
  3. 粗筛的 AABB 应逐段计算（每段自己的小 AABB），而不是整条路径一个大 AABB。
- 验收（静态）：`EraserEngine` 中出现线段-线段距离函数（如 `segmentDistance`），且 `eraseWhole`/`erasePartial` 在 `intersectsBounds` 通过后仍有第二层判定。

## R-10 【P1】像素擦的 maskPath 无分段：多次擦除之间会连出一条直线把笔画拦腰擦断

- 位置：`EraserEngine.ets:69`（`maskPath: stroke.maskPath.concat(eraserPath)`）、`core/adaptation/Canvas2DStrokeRenderer.ets:435-452`
- 证据 ✅：`renderEraserMask` 把整个 `maskPath` 当作**一条连续折线**描边：
```
c.moveTo(stroke.maskPath[0].x, stroke.maskPath[0].y);
for (let i = 1; i < stroke.maskPath.length; i++) { c.lineTo(...); }
```
而 EraserEngine 用 `concat` 直接把第二次擦除的路径接在第一次后面，中间**没有断点标记**。
- 用户可见现象：在一笔上擦两个不相连的位置，第一次擦的终点与第二次擦的起点之间会被"连线擦除"，凭空多出一道横穿笔画的缺口。
- 修复指令：`maskPath` 改为 `Point2D[][]`（多段），或插入哨兵点（NaN）分隔；`renderEraserMask` 每段独立 `beginPath()/moveTo()`。
- 验收（静态）：`renderEraserMask` 中 `beginPath()` 出现在循环内 / 每段一次；`maskPath` 类型或哨兵约定在 `StrokeTypes` 中有定义。

## R-11 【P1】擦除遮罩的 destination-out 会穿透到同一离屏层上已绘制的其它笔画

- 位置：`StrokeLayerManager.ets:114-127`（`renderStrokeOnto` 末尾无条件 `renderEraserMask`）+ `rebuildFromStrokes` 顺序绘制
- 证据 🟡（逻辑确定）：`rebuildFromStrokes` 按顺序把所有笔画画到**同一张** `completedCtx` 上，每画完一笔立即以 `destination-out` 应用该笔的 maskPath。`destination-out` 作用于整个目标画布，不限于当前笔画像素 → 会把**先前已绘制的其它笔画**在同一位置一并挖掉。
- 用户可见现象：像素擦某一笔时，压在它下面（更早画的）的其它笔迹也出现同样形状的缺口；而撤销时那些笔画的数据并没有变化，重建后缺口依旧 → 表现为"擦除会误伤别的笔画且擦不回来"。
- 修复指令：每个带 maskPath 的笔画渲染到**独立的临时离屏层**，在该层上应用 destination-out，再以 `source-over` 合成回主层。
- 验收（静态）：`renderStrokeOnto` 中带 maskPath 分支使用独立 OffscreenCanvas；主层上不再直接出现 `destination-out`。

## R-12 【P1】擦除遮罩坐标未随笔画 transform 走 → 变换后的笔画上「洞」位置错位

- 位置：`StrokeLayerManager.ets:117-126`
- 证据 ✅：`renderStrokeOnto` 先 `c.setTransform(stroke.transform)`，然后在**同一变换下**绘制 maskPath。但 maskPath 是擦除时记录的**页面坐标绝对值**，未经过 stroke.transform 的逆变换。
- 推演：一笔被像素擦出洞后再被选中移动 dx，stroke.transform 变为平移 dx；重绘时 maskPath 的点又被这个 transform 平移一次 → 洞相对笔画多移了 dx（等于洞相对屏幕移了 2dx）。
- 用户可见现象：移动/翻转带擦除缺口的笔画后，缺口跑到笔画外面，笔画看起来"缺口复原了"或在旁边多出一块被擦空的区域。
- 修复指令：擦除时把 eraserPath 用 `inverse(stroke.transform)` 变换到笔画本地坐标再存入 maskPath（推荐）；或渲染 mask 时临时 `restore` 掉 stroke.transform。
- 验收（静态）：`EraserEngine.erasePartial` 中出现对 `stroke.transform` 求逆并作用于 eraserPath；或 `renderEraserMask` 调用点在 `c.restore()` 之后。

## R-13 【P2】`StrokeSession.addBatch` 的活动态守卫写错：判断的是方法引用而非返回值

- 位置：`rendering/StrokeSession.ets:90`

## R-16 【P2】缩略图 setTransform 的 b/c 分量写反（转置）

- 位置：`ThumbnailRenderer.ets:73-74`
