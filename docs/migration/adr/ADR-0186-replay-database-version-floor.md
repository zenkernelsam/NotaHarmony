# ADR-0186：Replay 数据库版本使用下限契约

## 状态

Accepted，2026-08-14。

## 问题

26 个历史 D-02 replay 同时验证各自的 DDL/迁移内容，并额外要求
`DB_VERSION: number = 61`。Phase 207 合法升级到 v62 后，这些脚本在第一个版本断言即退出：

- 新增迁移会让所有旧功能 replay 伪失败，即使它们验证的迁移和运行逻辑完全未退化。
- fail-fast 遮蔽同一脚本后续真正可能过期的断言；`d02-pdf-background.mjs` 的旧 PDF 页数表达式就是在修复版本断言后才暴露。
- 把精确值机械更新成 62 只会把同一问题推迟到下一次数据库升级。

## 决策

1. 新增共享 `support/database-version.mjs`，从 `DatabaseHelper.ets` 解析唯一、行级、整数形式的 `export const DB_VERSION`。
2. 历史 replay 使用 `assertDatabaseVersionAtLeast(source, 61)`，表达“生产数据库不得回退到该功能集合之前”，而不是要求当前版本永远停在 61。
3. 每个 replay 仍保留其具体迁移编号、DDL、触发器和 reducer 行为断言；版本下限不能代替迁移内容验证。
4. 新增帮助器专项 replay，覆盖 v60 拒绝、v61/v62/三位数版本接受、缺失/小数/注释伪声明/重复声明拒绝，以及非法 minimum 拒绝。
5. 数据库最新版本的精确值继续由当前迁移专项门禁负责；旧功能 replay 不重复拥有“最新版本号”所有权。

## 结果

- 合法新增迁移不会批量破坏旧功能回归。
- 数据库版本回退到 v60 或更早仍会被全部相关 replay 拒绝。
- 全量 replay 可以继续执行到后续断言，从而暴露真实的测试/实现漂移。

## 边界

- 下限 61 是这些脚本迁移时已有功能集合的最低统一门槛；各具体历史迁移仍由脚本中的 v33-v60 等断言约束。
- 该决策只修改桌面 replay，不修改生产数据库版本、DDL、ArkTS 或 HAP 行为。
