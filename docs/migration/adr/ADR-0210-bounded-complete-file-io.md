# ADR-0210：文件读取、复制与内容比较必须有界且完整

## 状态

Accepted，2026-08-15。

## 问题

Phase 232 后继续复核所有生产 `readSync()` 路径，确认先前的短读修复已经不再丢弃返回值，但仍存在两类
数据完整性与内存边界偏差：

1. `NoteImporter`、`NoteExporter` 与 `ImageAssetPackageStore` 每轮都按“全部剩余长度”创建临时
   `ArrayBuffer`。读取大文件时，除最终输出外还会瞬时分配近似文件大小的第二个缓冲。
2. 录音资产与系统 Backup 的逐文件比较同时各读一次，并要求两次 `readSync()` 返回完全相同的长度。
   两个内容相同的文件如果出现不同的合法短读节奏，会被误判为冲突或快照变化。

其中 Note 导出更严重：`exportNote()` 返回的完整 `data` 仍在作用域内，旧实现又把临时文件完整读成第二个
`bytes`，再写入 picker 目标。图片已有文件比较也会同时持有 `expected`、完整 `actual` 与一次接近完整文件的
临时读取缓冲。

## 原版依据

- `jv5.f()` 用 `BufferedOutputStream(..., 8192)` 接收 URI 输入。
- `fag.z()` 固定创建 `byte[8192]`，循环 `read()`，并只写入每次实际返回的 `i` 字节。
- 原版资产落盘 `re0.g()` 通过 `DigestOutputStream` 调用 `fag.y()`。
- `fag.y()` 调用 `l96.i0(..., 65536)`；`l96.i0()` 只创建一个固定大小缓冲，并循环读写到 EOF。

原版的共同契约不是“必须使用某个唯一缓冲大小”，而是：大对象通过固定大小缓冲流式传输；每次只消费实际
读取长度；短读不会改变后续字节身份。

## 决策

1. Note 导入、Note 导出和图片资产 I/O 的单次临时缓冲上限统一为 64 KiB。
2. `readFileFully()` 在调用方确实需要聚合 `Uint8Array` 时保留最终输出，但临时读取只能按有界块分配。
3. Note 导出不再把临时 `.note` 完整读入第二个数组；改为从临时文件向 picker 目标流式复制。
   完整导出数组在临时文件同步落盘后立即释放，不能跨系统 picker 的异步等待继续存活。
4. 所有读取和写入循环必须拒绝零、负数以及超过本次请求长度的异常进度。
5. 传给 `writeSync()` 的 `ArrayBuffer` 必须严格覆盖本次有效字节视图，不能泄漏 backing buffer 的前后区域。
6. 图片已有文件比较改为直接把每个读取块与 `expected` 对应区间比较，不再构造完整 `actual`。
7. 两文件比较必须分别把同一逻辑块读满，再逐字节比较；不能要求两边单次系统调用返回相同长度。
8. 保留现有文件句柄 `finally` 所有权、`fsync`、原子 rename、数据库事务和失败清理语义。

## 结果

- Note 导入和图片读取的额外临时内存由近似文件大小降为最多 64 KiB。
- Note 导出不会跨 picker 等待保留完整归档，也不再创建第二份完整归档；目标写入仍覆盖所有短读和短写。
- 图片已有文件比较不再复制完整文件，图片落盘也不再复制“全部剩余字节”。
- 录音去重与系统 Backup 快照校验不会因左右文件短读分段不同而误报冲突。
- 实际读取不足、零进度或平台返回不可能的超长进度仍会失败关闭，不会静默补零或截断。

## 边界

- 当前 ZIP parser 和图片解码/导出接口仍要求最终 `Uint8Array`，因此 Note 导入与资产读取仍需持有一份完整
  结果；本决策消除的是额外的文件大小级临时副本。
- CoreFileKit picker URI、网络挂载短读和 I/O fault injection 仍需真机验证。
- 本阶段没有启动设备、模拟器、虚拟机或 Hypium。
